## 0. 项目全景与开发流程

### 0.1 使用说明

- 每个业务模块按统一模板：**功能 → 开发任务（勾选 + 估点）→ 具体结构（目录 + 关键签名）→ 需要什么 → 验收**。
- 估点单位 `h`（小时），单人 20h/周 × 6 周 ≈ 120h；标注 **P0**（必做）/ **P1**（可延后）——时间不够砍 P1，别砍质量。
- 每个任务完成即打勾；每完成一个模块跑一次验收命令，**没有可运行产物不视为完成**。
- 开发顺序：**先按 §0.5 跑通 walking skeleton，再按 §1.1 依赖图逐个填模块**，不要跳着做。

**不重复、见设计文档 v2.3 的内容**（开发到对应处直接翻阅设计文档）：完整错误码表（§5.3）、30 条扰动用例清单（附录 A）、6 个 Prompt 模板（附录 C）、淘宝/京东字段映射表（附录 F）、完整配置样例（§6.2）、定时任务清单（§9.1.1）、DID 公式（§3.9）、完整 DDL（§4.2）。

### 0.2 整体分层（一个完整后端项目的骨架）

```text
① 应用外壳 App Shell   入口 / 配置 / DI / 生命周期 / 启动自检
② 接口层   API         路由 / 请求响应 schema / 统一错误处理 / 分页
③ 编排层   Pipeline    端到端数据流 + run 状态机（把 M1–M9 串成一条线）
④ 业务模块 Domain      M1 DQE · M2 沙箱 · M3 归因 · M4 分析 · M5/M6 网关执行 · M9 复盘
⑤ 数据层   Persistence ORM / 迁移 / Repository
⑥ 基础设施 Infra       Trace / 日志 / 评测 / 部署
```

> ①—③ 是"骨架"，④ 是"零件"，⑤⑥ 是"底座"。**没有骨架，零件再全也不是一个项目。**

### 0.3 应用外壳（App Shell）

**功能**：把各模块装配成一个可启动、可关闭、可自检的应用。

```text
hub/
├── app.py            # create_app() -> FastAPI；注册路由、中间件、生命周期
├── di.py             # 依赖装配：Settings/Repos/Engines/LLM 客户端，一处创建处处注入
├── lifespan.py       # 启动自检 + 优雅关闭
└── main.py           # 开发用 uvicorn 入口
```

```python
# app.py
def create_app(settings: Settings) -> FastAPI:
    app = FastAPI(title="E-commerce Operation Hub", version="0.1.0")
    container = build_container(settings)        # di.py
    register_routers(app, container)             # §0.6 全部路由
    app.state.container = container
    return app
```

**启动自检清单**（失败即退出，见设计 §6.3）：`sandbox_dir` 在 tmpfs、`gateway.deny_by_default=true`、DB 迁移最新、LLM 配置非空（缺了给明确提示）。

**开发任务**

- [ ] S0.1 `di.py` 依赖容器（settings/repos/engines/llm）——1h
- [ ] S0.2 `app.py` + `lifespan.py`（启动自检 + 优雅关闭）——1.5h
- [ ] S0.3 统一异常处理中间件（`HubError` → 标准 JSON `{code,message,trace_id}`）——0.5h

### 0.4 编排层（Pipeline + 状态机 + 数据流）

**功能**：把 M1–M9 串成一条端到端流水线，定义"一次分析"的生命周期。

```text
pipeline: ingest(P0) → dqe(M1) → multimodal(M2) → graph(M3)
        → analysis(M4) → gateway/execution(M5/M6) → retro(M9)
```

```python
# pipeline/pipeline.py
STEPS: list[Step] = [
    Step("ingest",     fn=ingest.run,      requires=[]),
    Step("dqe",        fn=dqe.run,         requires=["ingest"]),
    Step("multimodal", fn=multimodal.run,  requires=["dqe"]),
    Step("graph",      fn=graph.run,       requires=["multimodal"]),
    Step("analysis",   fn=analysis.run,    requires=["graph"]),
    Step("gateway",    fn=gateway.run,     requires=["analysis"]),
    Step("retro",      fn=retro.run,       requires=["gateway"]),
]

async def run_pipeline(batch_id, ctx) -> RunResult:
    # 按拓扑排序执行；每步落库；失败断点续跑；每步写 span
```

**Run 状态机**

```text
batch:  PENDING → RUNNING → DONE / FAILED（可重跑，幂等）
run:    QUEUED → RUNNING → DONE / DEGRADED / FAILED
```

**数据流对象链**（各模块的输入输出，即"数据怎么流转"）

```text
RawBatch → Record → DQEVerdict → Extracted/Classification/Validation
        → IssueCluster/Anomaly → ActionProposal → ToolExecution
        → ActionOutcome → CaseEntry
```

**开发任务**

- [ ] P1 `pipeline/` 包 + `Step` 定义 + 拓扑排序 + 断点续跑——3h
- [ ] P2 run/batch 状态机 + 落库——2h
- [ ] P3 `make skeleton`：假 batch 走完整条 pipeline（模块先 stub）——2h

### 0.5 Walking Skeleton（第一周重定义）

**第一周的目标不是"做完 M1"，而是"一条假数据走完整条流水线"。**

```text
D1–D2  契约层（B0.4）+ 应用外壳（S0）+ pipeline 骨架（P1）
D3–D4  适配器真实现（真实文件）+ DQE 规则轨真实现，其余模块 stub
D5      make skeleton：一份真实文件 → 走完整条 pipeline → 输出 RawBatch + verdict（其余为 mock）
```

**判断标准**：周五结束时，`make skeleton` 能一条命令跑通"文件 → 报告"，哪怕中间 M3–M9 都是假实现。**有这条线，才叫"项目"；没有，就是"一堆模块"。**

### 1.4 通用工程约定

```text
hub/
├── core/           # config.py / errors.py / logging.py / tracing.py / di.py
├── contracts/      # 全部 Pydantic 契约（唯一真相，禁止反向依赖）
├── persistence/    # sqlalchemy models / repository / migrations
├── ingress/        # 适配器（3.12）
├── dqe/            # M1
├── multimodal/     # M2
├── graph/          # M3（LangGraph）
├── analysis/       # M4
├── gateway/        # M5
├── execution/      # M6
├── scheduler/      # M7
├── eval/           # M8
├── retro/          # M9
├── cli.py          # hub 命令入口
└── tests/
```

**五条硬规矩**（违反即返工）：

1. **契约先行**：任何模块的输入输出先写进 `contracts/`，实现只能 import 契约，不能绕过；
2. **`impl` 必填**：凡有可替换实现（规则/ML/LLM）的输出，必须带 `impl` 字段；
3. **错误统一**：抛 `HubError(code, message, retryable)`，禁止裸 `except`；
4. **依赖单向**：`web/application → 模块 → contracts`，`contracts` 不依赖任何模块；
5. **每模块可单独跑**：一个 `hub run <module>` 或 `make <module>` 命令，缺数据也要能报出清晰错误而非崩栈。

### B1 存储层（5h）

**功能**：SQLAlchemy 2.0 模型 + Repository 抽象；dev 用 SQLite，生产切 PG15（只改一行 URL）。

**开发任务**

- [ ] B1.1 `persistence/models.py`：落地 §4.2 的核心表（先 `batch/raw_sheet/record/extraction/classification/validation/anomaly/tool_call/trace_span`，`case_entry` 等 M4/M9 需要时再加）——2h
- [ ] B1.2 `persistence/repository.py`：`BatchRepo/RecordRepo/...`，统一 `get/upsert/list` 接口——2h
- [ ] B1.3 `alembic init` + 首版迁移——1h

**具体结构**

```python
# persistence/repository.py
class BatchRepo:
    def get(self, batch_id) -> Batch | None: ...
    def upsert(self, batch) -> None: ...
```

**功能**：回复闭环、通知、报表生成、权限审计、知识沉淀——**纯后端逻辑，不含前端页面**（页面后续再做）。本模块对应的 API 已在 §0.6 列出（/reply-drafts、/reports、/auth、/admin/audit、/knowledge 等），这里是它们的实现指南。

**开发任务**

- [ ] M10.1 回复草稿（`review_reply_draft`：生成 → 合规校验 → 审批 → 发送，状态机 `DRAFT→APPROVED→SENT`）——3h
- [ ] M10.2 通知 outbox（`notification` 表 + 异步派发 + 唯一键幂等 + 10 分钟合并）——2h
- [ ] M10.3 报表生成（`report_job` + 聚合白名单渲染，上下文不得含原文/PII）——3h
- [ ] M10.4 权限/租户/审计（`tenant/app_user/audit_log` + JWT + RBAC 中间件 + append-only 审计）——2h

**具体结构**

```text
collab/
├── reply.py          # 回复草稿闭环（合规词拦截：保证/赔偿/百分百）
├── notify.py         # outbox 通知（先落库，渠道 P1 再接）
├── report.py         # 报表渲染（白名单字段 + 行数上限）
└── auth.py           # JWT + RBAC + 审计
```

**需要什么**：前置 B0/B1、网关（L3 发送要审批）；SMTP/企微 webhook（通知 P1 可先落库不真发）。

**验收**：回复草稿走完 `DRAFT→APPROVED→SENT`；报表渲染上下文不含原文/PII；越权访问返回 403 并留审计记录。

## 16. 部署与运行

**本地开发（最快跑起来）**

```bash
pip install -r requirements.txt
alembic upgrade head                    # dev 用 SQLite，零配置
cp .env.example .env                    # 填 HUB_LLM_BASE_URL / HUB_LLM_MODEL / HUB_LLM_API_KEY
uvicorn hub.app:create_app --factory --port 8080
make doctor && make skeleton            # 健康表 + 骨架跑通
```

**生产形态（docker compose，见设计 §9.1）**

```yaml
services:
  api:      {build: ., command: "uvicorn hub.app:create_app --factory"}
  worker:   {build: ., command: "python -m hub.scheduler.worker"}
  postgres: {image: postgres:15}
  redis:    {image: redis:7}
```

**环境变量**：`HUB_LLM_BASE_URL / HUB_LLM_MODEL / HUB_LLM_API_KEY / HUB_DB_URL / HUB_REDIS_URL / HUB_VISION_MODEL`。

**数据库迁移**：模型改动 → `alembic revision --autogenerate` → `alembic upgrade head`（只做向前兼容变更，不 drop 列）。
