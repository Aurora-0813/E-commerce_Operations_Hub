## 4. 实现思路

### 4.1 M7 调度（scheduler/）

#### 队列模型

```text
hub:tasks（Stream）  ── XREADGROUP(consumer group: hub-workers) ──► worker
      │                                                             │
      │◀──────────── XACK（成功确认）/ XAUTOCLAIM（回收僵死）──────┘
      └── 尝试 ≥ 3 次 ──► hub:dlq（死信）──► 告警 + hubctl dlq replay
```

| 项 | 设计 |
| --- | --- |
| 消息体 | `{task_id, type, run_id, batch_id, tenant_id, attempt, enqueued_at}` |
| 消费组 | `hub-workers`，每个 worker 唯一 consumer name |
| 回收 | `XAUTOCLAIM` 间隔 60s，`min-idle=300s`，防 worker 崩溃丢消息 |
| 重试 | `attempt < 3` 重新入队（`attempt+1`） |
| 死信 | 超限 → `hub:dlq` + `dead_letter` 表 + 告警 + 重放 CLI |
| 并发 | 全局 32 / 单租户 8 / LLM 8（asyncio.Semaphore） |

#### 三条硬保证

1. **至少一次投递 + 幂等消费**：任务入口按 `task_id` 建唯一索引，重复消费直接返回上次结果；
2. **批次互斥**：同一 `batch_id` 用锁保证不并发分析；
3. **时间基准**：统一 `Asia/Shanghai` 存 `timestamptz`，跨时区数据在适配器层已归一。

#### 三类触发

| 触发 | 实现 |
| --- | --- |
| 事件 | 文件导入成功后 `XADD`；工具执行完成回调 |
| 条件 | 定时扫描近 24h 指标，命中阈值（差评率环比 +30%）→ 生成 Run |
| 定时 | 每日 02:00 全量重算、03:00 复盘扫描、07:30 数据拉取（cron 表见设计文档） |

### 4.2 M9 效果复盘（retro/）

#### 观察窗口与对照组

| 动作等级 | 观察窗口 | 基线窗口 |
| --- | --- | --- |
| L1 | 7 天 | 前 14 天 |
| L2 | 14 天 | 前 14 天 |
| L3 | 30 天 | 前 28 天 |

对照组选取（5 条，缺一不可）：同 `category_l2` + 同平台 → 价格带 ±20% → 基线窗口内**无任何动作** → 基线指标 CV ≤ 0.5 → 数量 ≥ 5。

#### DID 计算（did.py）

```text
对指标 m（差评率、退款率、转化率、GMV、评分均值）：
  treat_delta = m_post(T) - m_pre(T)
  ctrl_delta  = m_post(C) - m_pre(C)          # C 取对照组均值
  effect_m    = treat_delta - ctrl_delta      # DID 估计量，已剔除大盘波动

置信区间：对照组 bootstrap 1000 次，取 effect 的 2.5% / 97.5% 分位
显著性  ：|effect_m| ≥ threshold 且两个子窗口方向一致
```

#### 结论判定（conclude.py）

| 结论 | 条件 |
| --- | --- |
| `POSITIVE` | ≥2 指标显著正向，无显著负向 |
| `NEGATIVE` | ≥1 主指标显著负向 |
| `NEUTRAL` | 无显著 |
| `INCONCLUSIVE` | 对照组不足 / 撞大促 / 数据覆盖 <80% / 动作执行失败 |

**核心原则：宁可 INCONCLUSIVE，不给假结论。** 对照组不足 5 个、窗口撞大促、数据缺 20% 以上，一律 `INCONCLUSIVE` 并给 `reason_code`——**面试讲"改了有没有用"，最值钱的就是这句"算不清时我诚实说不算"**。

#### 回写案例库（闭环）

```text
POSITIVE → 生成 playbook 草稿 → 人工审核 → 发布为 case_entry（供 Case RAG 检索）
NEGATIVE → 生成回滚建议工单 + 同样入库（"别这么做"的负例）
NEUTRAL/INCONCLUSIVE → 不入库
```

**这是 07 Case RAG 的数据来源**——复盘结论 = ground truth，案例库越用越准，闭环成立。

## 9. 常见坑

1. **至少一次 ≠ 最多一次**：队列默认至少一次，不幂等就会重复扣费/重复执行。**消费端必须幂等**；
2. **XACK 过早**：拿到消息就 ACK，结果处理一半崩了消息就丢了。**处理成功后才 XACK**；
3. **重试无上限**：一直失败一直重试，队列被毒消息堵死。**最多 3 次进 DLQ**；
4. **复盘拿前后对比当效果**：大促/季节会让"前后对比"全是假信号。**必须对照组 DID**；
5. **对照组不足还硬给结论**：3 个对照组就敢说"提升 20%"，面试一追就崩。**INCONCLUSIVE 是合法的诚实答案**；
6. **DID 用随机切分**：时间序列随机切会泄漏未来信息。**必须按时间切**；
7. **POSITIVE 没回写案例库**：复盘结论只进报表不进 `case_entry`，Case RAG 就没数据。**回写是闭环的最后一环**。
