## 4. 实现思路

### 4.1 工具声明（spec.py）

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str                    # 全局唯一，如 crm.ticket.create
    version: str                 # 语义化，用于幂等键与回放
    description: str             # 供 LLM 选择
    params_model: type[BaseModel]  # 参数 JSON Schema 来源
    risk_level: RiskLevel        # L0-L3
    scopes: frozenset[str]       # 所需权限
    idempotent: bool
    timeout_s: float
    rate_limit: RateLimit        # qps / burst
    evidence_types: frozenset[str]  # 必须提供的依据类型
    compensate: str | None       # 补偿动作名（None = 不可补偿 → 必须 HITL）
```

**核心思想**：工具的**能力**和**治理**分离——`params_model` 描述"能干什么"，`risk_level/scopes/evidence_types/compensate` 描述"能不能干、怎么监督"。新增工具 = 填一张 spec + 写一个 handler，主流程零改动。

### 4.2 注册表（registry.py）

```python
@register(risk_level=RiskLevel.L1, idempotent=True, ...)
async def create_ticket(...) -> ToolResult: ...

registry.get("crm.ticket.create")   # 查工具
registry.available()                # 过滤 health() 失败的（供 make doctor）
```

**好处**：`make doctor` 打印工具健康表，启动时自检"哪些工具可用、哪些依赖缺失"。这是"系统化"的直观证据。

### 4.3 四道防线（guards.py，核心中的核心）

**顺序不可交换**，逐道讲：

```python
async def invoke(call, ctx) -> GatewayResult:
    # ① 存在性 + 参数 + 权限
    spec = registry.get(call.tool)                   # 未注册 → CPP-5001
    args = spec.params_model.model_validate(call.args)  # 类型/边界/必填
    if not ctx.has_scopes(spec.scopes):
        return deny("CPP-5002 SCOPE_DENIED")

    # ② 依据校验（L1 及以上必须带证据依据）
    if spec.risk_level >= RiskLevel.L1:
        ok, missing = evidence.check(spec.evidence_types, call.evidence_refs, ctx.state)
        if not ok:
            return deny("CPP-5003 EVIDENCE_MISSING", missing)

    # ③ 幂等（先查）
    key = idem_key(spec, args, ctx.tenant, ctx.run_id)
    if (prev := await idem.lookup(key)):
        return prev                                   # 命中即重放，不重复执行

    # ④ 频控（令牌桶）
    if not await limiter.acquire(f"{ctx.tenant}:{spec.name}", spec.rate_limit):
        return deny("CPP-5005 RATE_LIMITED", retry_after=...)

    # ③ 幂等（后占位，执行前原子占位）
    if not await idem.claim(key):
        return await idem.replay(key)                 # 并发竞态，另一请求已占位

    # ⑤ 分级执行
    if spec.risk_level >= RiskLevel.L3:
        return await hitl.enqueue(...)                # 永不直接执行
    if spec.risk_level == RiskLevel.L2 and not ctx.has_approval():
        return await approval.request(...)
    return await execute(spec, args, ctx)             # 交 M6
```

**幂等"先查后占位"为什么关键**（最容易写错的地方）：

- 查询放**频控前**：命中就快速重放，不浪费限流额度；
- 占位放**频控后**：被限流时不白白占用幂等键，允许之后重来；
- 占位用 SETNX + DB 唯一索引双保险（Redis 挂了 DB 兜底）。

### 4.4 风险分级（risk.py）

| 等级 | 定义 | 示例 | 处置 |
| --- | --- | --- | --- |
| L0 | 只读 | 查库存、查工单状态 | 直接执行 |
| L1 | 可逆、无对外影响 | 生成 FAQ 草稿、建草稿任务 | 自动执行 + 全量审计 |
| L2 | 影响有限、需留痕 | 派发内部工单、改内部标签 | 需审批（超时默认拒绝） |
| L3 | 不可逆/对外/资金 | 改价、下架、批量回复客户 | **硬拦截 → HITL** |

**默认拒绝**：`deny_by_default=true`，未注册/未声明 scope/未声明依据 → 一律拒绝。

### 4.5 执行链 E1–E5（execution/）

```text
E1 动作决策（LLM 从 allowlist 选工具，风险 ≤ auto_execute_max_risk）
E2 强校验（网关四道防线）
E3 调用工具（超时 + 仅可重试错误 + 指数退避 + 熔断）
E4 状态回查（独立查询真实状态，不信工具返回值）
E5 成功→归档；失败→补偿（compensate）→ 仍失败→工单升级
```

**重试策略（E3）**：

| 错误 | 重试？ | 说明 |
| --- | --- | --- |
| 超时/5xx/429 | 是，≤3 次 | 退避 [1s,4s,16s] + 抖动，携带同一幂等键 |
| 4xx 参数/权限/依据 | 否 | 逻辑错误，重试只会放大成本 |
| L3 拦截 | 否 | 转 HITL，禁止自动重试绕过 |
| 熔断 open | 否 | 5 次失败/60s → open 30s → 半开单探针 |

### 4.6 状态回查（verifier.py，反幻觉最后一公里）

**问题**：LLM 经常"自作聪明"告诉系统"已派单成功"，但工具其实报错了。

**解决**：执行后不信工具返回值，系统用代码去查真实状态：

```python
async def verify_ticket(handle, ctx) -> VerifyResult:
    got = await crm_client.get_ticket(handle.external_id)
    if got is None:
        return VerifyResult(ok=False, reason="NOT_FOUND")
    if got.status == "closed" or got.subject != ctx.expected.subject:
        return VerifyResult(ok=False, reason="STATE_MISMATCH")
    return VerifyResult(ok=True, snapshot=got.model_dump())
```

**规则**：`verify_failed ≥ 2` → `status=FAILED_VERIFIED` → 执行 `compensate` → 生成 HITL 工单 + 告警。**任何情况下不得仅凭工具返回 ok=true 标记成功。**

### 4.7 补偿注册表（compensator.py）

| 工具 | 补偿 | 幂等 |
| --- | --- | --- |
| `crm.ticket.create` | `crm.ticket.close` | 是 |
| `kb.faq_draft.save` | `kb.faq_draft.delete` | 是 |
| `item.tag.update` | 恢复上一版本快照 | 是 |
| `item.price.update` | **不提供自动补偿**（L3） | — |

**规则**：`compensate is None` 的工具，风险等级**强制提升到 L3**（不可补偿就必须人工）。

## 9. 常见坑

1. **四道防线顺序乱**：把幂等放频控前、占位放频控后，逻辑就错了。**顺序不可交换，且幂等是"先查后占位"两段式**；
2. **默认允许**：漏了 `deny_by_default`，未注册工具就放行，等于裸奔。**默认拒绝是底线**；
3. **信了工具返回的 ok**：LLM 说"派单成功"就信了，没回查真实状态——这是幻觉最后一公里。**E4 回查是硬约束**；
4. **L3 也能自动重试绕过**：L3 拦截后走重试逻辑，等于变相绕过人工。**L3 禁止自动重试**；
5. **不可补偿工具没升 L3**：改价这种不可逆操作没标"不可补偿"，失败时没退路。**compensate=None → 强制 L3**；
6. **工具和工序写重复**：同一段逻辑既在 pipeline 里又在 tool 里。**工具是能力单元，工序是编排单元，逻辑只写一处**。

### 实际踩到的 5 个（前 4 个是同一类错误）

| # | 坑 | 本质 |
| --- | --- | --- |
| 1 | 提示词里塞固定话术 → 10 条回复一模一样，对"物流慢"答非所问 | **把"表达"写死了** |
| 2 | 分布硬编码"本款偏小"（实际可能偏大） | **把"事实"写死了** |
| 3 | 让 LLM 润色描述 → "肩宽对不上"变"肩部宽松适肩" | **让 LLM 改了事实的倾向** |
| 4 | 问"描述里缺什么" → 输出"未说明肩宽问题"（给商家看的，不是给买家看的） | **搞错了"说给谁听"** |
| 5 | `model_dump()` 保留 `Decimal` → 写 JSONB 崩 | 要 `mode="json"` |

**通用判据**：

```text
可以硬编码的：流程 / 规则 / 话术框架   （"会反馈给工厂"）
不能硬编码的：事实 / 数值 / 结论       （"本款偏小""降价 5%"）
```

## 第二阶段：双端互通（半自动回流）

> 挂在 M6 执行链下的人工执行分支，让"建议"真正落到平台，补上"单向读"缺的"动作写回"。

**执行清单 + 回填机制**：

```text
审批通过 → 路由判断
  ├─ L0/L1 → 系统调工具自动执行（现有）
  └─ L2/L3 → 进「待执行清单」
        → 运营导出清单（Excel：动作 / 商品 / 目标值 / 理由）
        → 平台手动执行
        → 回填「已执行 / 失败」
        → 触发复盘观察窗口
```

**实现**：`execution_list` 表（action / 目标 / 理由 / 状态）+ 回填接口 `POST /executions/{id}/confirm` + 回填后触发 M9 复盘。

**边界**：不碰 RPA、不碰平台 API 权限，人仍是"动手"的一方——守住"AI 只动脑"。

**验收**：一个 L3 动作走完"清单 → 回填 → 复盘"完整闭环。
