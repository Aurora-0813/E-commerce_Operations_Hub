# 02 · 项目骨架与契约层

> 上一篇：01 前期准备与环境搭建 ｜ 下一篇：03 数据接入与 PII（适配器）

## 1. 目标

搭起整个后端项目的**骨架**：应用外壳 + 契约层 + 依赖装配 + CLI + walking skeleton。做完这篇，你能启动一个服务、能通过命令行调起一条"假数据走完整条流水线"的链路——**哪怕中间模块全是空壳，这条线已经通了**。

**这是全项目最重要的一个阶段**：骨架定错，后面所有模块都要返工。宁可多花半天，把接口边界想清楚。

## 2. 架构总览（先看懂这张图再动手）

```text
┌ 应用外壳 app.py / lifespan.py ──────────────────────────┐
│   create_app() → 注册路由/中间件 → 启动自检 → 优雅关闭    │
├ 依赖装配 di.py ────────────────────────────────────────┤
│   一处创建 Settings/Repos/Engines/LLM，处处注入           │
├ 契约层 contracts/ ─────────────────────────────────────┤
│   全项目唯一的 Pydantic 模型（模块间只靠契约通信）         │
├ 编排 pipeline/ ────────────────────────────────────────┤
│   STEPS 拓扑排序 + run 状态机 + 断点续跑                 │
├ 业务模块（03 起逐个填） dqe/ multimodal/ graph/ ...       │
└ 基础设施 core/ config/errors/logging/tracing ──────────┘
```

**铁律：契约先行。** 任何模块的输入输出，先定义成 `contracts/` 里的 Pydantic 模型，再写实现。实现只能 import 契约，不能绕过。

### 3.2 目录与组织

```text
contracts/
├── __init__.py       # 集中 re-export，模块只 from hub.contracts import X

├── quality.py        # DQEVerdict/Validation

├── retro.py          # ActionOutcome/OutcomeEffect
└── case.py           # CaseEntry/RetrievedCase/CaseAugmentedSuggestion
```

### 3.3 关键约定（写进 README）

1. 枚举用 `StrEnum`（业务枚举）或 `IntEnum`（风险等级，要能比大小）；
2. 金额用 `Decimal`，**禁止 float**；时间用 `datetime`（带 tz）；
3. 凡"可替换实现"的结果，必须带 `impl: str` 字段；
4. 每个模型配一条"合法构造 + 非法构造"的契约单测。

## 4. 配置层（core/config.py）

```text
优先级：环境变量 > config/{env}.yaml > config/base.yaml
```

```python
class Settings(BaseSettings):
    app: AppConf          # env / out_dir
    storage: StorageConf  # url（sqlite:/// 或 postgresql+psycopg://）
    llm: LLMConf          # base_url / model / temperature / api_key
    dqe: DqeConf          # engine / 阈值 / model_dir
    gateway: GatewayConf  # deny_by_default / auto_execute_max_risk
```

**实现思路**：`pydantic-settings` 的 `BaseSettings` + 自定义 `settings_customise_sources` 把 YAML 作为底、env 作为顶。启动时 `Settings.load(env="dev")` 一次加载，全局只读。

## 5. 错误层（core/errors.py）

```python
class HubError(Exception):
    code: str          # 如 "CPP-1001 HEADER_NOT_FOUND"
    message: str
    retryable: bool = False
    def to_dict(self) -> dict: ...   # {code, message}
```

**实现思路**：只定义一个 `HubError` + 一张错误码常量表（CPP-1xxx~6xxx，抄设计文档 §5.3）。业务代码一律 `raise HubError(...)`，FastAPI 全局异常中间件捕获并转成 `{code, message, trace_id}`。**禁止裸 `except Exception`。**

## 6. 依赖装配（di.py）

```python
class Container:
    settings: Settings
    db: Engine / SessionFactory
    llm: LLMClient
    repos: ...          # 03 再补
    def wire(self) -> None: ...   # 启动自检 + 插件健康探测

def build_container(settings) -> Container: ...
```

**实现思路**：一个 `Container` 实例挂在 `app.state` 上，各模块通过 `request.app.state.container` 取依赖。**不要用全局单例**（难测试），走 DI。

## 7. 应用外壳（app.py / lifespan.py）

```python
def create_app(settings) -> FastAPI:
    app = FastAPI(title="E-commerce Operation Hub", version="0.1.0")
    container = build_container(settings)
    register_routers(app, container)     # 03 起逐批加路由
    app.state.container = container
    return app
```

**启动自检（lifespan，失败即退出）**：

1. DB 能连 + `alembic` 版本最新；
2. LLM 配置非空（缺了给清晰提示，不静默）；
3. `gateway.deny_by_default=true`；
4. 各插件的 `health()` 探测，不可用则打日志从链路剔除（不崩）。

## 8. CLI 与 Makefile

```bash

hub run <module>  # 单独跑某模块
hub skeleton      # walking skeleton
```

```make
doctor: ; python -m hub.cli doctor
skeleton: ; python -m hub.cli skeleton
test: ; pytest -q
```

**实现思路**：CLI 用 `argparse` 子命令，内部调 `di.build_container` 拿到依赖，复用和 API 完全相同的业务代码（CLI 与 API 只是两个入口，不重复逻辑）。

## 9. Walking Skeleton（本阶段的核心产出）

### 9.1 什么是 skeleton

一条 `pipeline`，把 7 个步骤串起来；每个步骤先指向一个 **stub 实现**（返回空结果/假数据），保证"假数据能从头走到尾"。

```python
# pipeline/pipeline.py
STEPS = [
    Step("ingest",     fn=ingest.run,      requires=[]),
    Step("dqe",        fn=dqe.run,         requires=["ingest"]),
    Step("multimodal", fn=multimodal.run,  requires=["dqe"]),
    Step("graph",      fn=graph.run,       requires=["multimodal"]),
    Step("analysis",   fn=analysis.run,    requires=["graph"]),
    Step("gateway",    fn=gateway.run,     requires=["analysis"]),
    Step("retro",      fn=retro.run,       requires=["gateway"]),
]

async def run_pipeline(batch_id, ctx) -> RunResult:
    # 拓扑排序 → 逐个执行 → 每步落库 + 写 span → 失败断点续跑
```

### 9.2 stub 模块长什么样

```python
# dqe/__init__.py（本阶段先 stub，03/04 换成真实现）
async def run(ctx) -> dict:
    return {"verdicts": [], "impl": "stub"}     # 空结果，但契约正确
```

**关键**：每个 stub 必须**返回正确的契约结构**（哪怕是空的），这样 pipeline 的落库、Trace、错误处理都能被真实跑通，只是业务逻辑是假的。

### 9.3 数据流（skeleton 跑通后要能看到）

```text
make skeleton
  → 造一个假 batch
  → ingest.run  返回 RawBatch（stub 或造假）
  → dqe.run     返回 []（stub）
  → ... 直到 retro.run 返回 []
  → 汇总：batch.status=DONE + 一份 run_manifest.json + 各步 span
```

## 12. 常见坑

1. **契约和实现耦合**：实现里 `from dqe.pipeline import X` 而不是 `from contracts import X`——一旦这样，模块间就锁死了，插拔机制失效；
2. **循环依赖**：`contracts` 绝不能 import 任何业务模块；`di` 不能 import 具体实现（用延迟导入/注册表）；
3. **启动自检太严格**：一开始 LLM Key 没配就 `exit(1)`，会让 `make doctor` 都起不来——正确做法是"缺了给警告，只有合规硬开关才拒绝启动"；
4. **skeleton 用真数据卡住**：skeleton 阶段用**假数据**，别在这里就接真实文件解析（那是 03 的事），否则骨架永远搭不起来；
5. **CLI 和 API 写了两遍逻辑**：入口只做"参数解析 + 调同一个函数"，业务逻辑只写一份。
