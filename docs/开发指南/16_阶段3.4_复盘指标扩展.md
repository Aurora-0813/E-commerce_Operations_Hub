# 16 · 阶段 3.4 复盘指标扩展：**先看数据，然后改了结论**

> 路线图 §8.4 的原话：
> **"本阶段第一步是『先看数据』，不是写规则"**
> "……**不要先写规则再看数据** —— 那是『让数据符合结论』" ✅
>
> 实测：2026-11-01 ｜ 40 个 observation ｜ 数据源 `action_outcome` + `record` + `sales_daily`

---

## 1. 原本要做什么（路线图 §8.2）

```text
M9 现在只看 neg_rate（差评率）
   ↓
差评率降了、但退款率升了 → "只安抚了情绪，没解决货的问题" ✅
   而这种现在会被判 POSITIVE —— 那是错的 ✅
   ↓
所以想加两个指标进**判定**：
   POSITIVE    : neg_rate 显著下降 **且** refund_rate 不显著上升
   INCONCLUSIVE: neg_rate 降但 refund_rate 显著升（reason=REFUND_WORSENED）
```

## 2. 先看数据（`scripts/probe_refund_corr.py`）

**方法**：按 observation 逐个算
`Δ差评率`（基期 → 干预后）与 `Δ退款率`（同窗口），看是否**同向变化** ✅

**结果**：

```text
可用样本：40 个
同向变化：**21 / 40 = 52.5%**
   ↓
52.5% ≈ 抛硬币（随机就是 50%）✅
   ↓
**差评率和退款率在这份数据里几乎无关** ✅
```

## 3. 为什么无关（不是偶然）

```text
`generate_mock.py` 里退款是**独立随机数**：
   refund = gmv × uniform(0.01, 0.03)     ← 和差评**没有任何耦合** ✅
   ↓
所以"差评降 → 退款降"这个业务假设，**在这份 mock 数据里不成立** ✅
   ↓
如果硬把它写进判定：
   · 会造出"看起来更严格"的规则 ✅
   · 但实际上是在**用随机数判定业务效果** ✅ ✗
   · 而 `hub retro` 的 4 组结论（G1 POSITIVE / G2 INCONCLUSIVE /
     G3 NEGATIVE / G4 撞大促）会**随机地**变成别的结论 ✅
```

## 4. 所以怎么做（按 §8.4 的 ② 条）

| 指标 | 进判定吗 | 说明 |
| --- | --- | --- |
| `neg_rate` | ✅ **进** | 已有，是判定依据 |
| `refund_rate` | ❌ **不进** | **只作展示**（本次结论） |
| `conversion` | ❌ **不进** | 同上 |

**具体实现**：
- `hub/retro/metrics.py` 新增 `sales_rates()`：按窗口返回 `refund_rate` / `conversion`
- `hub/retro/report.py` **打印**这两个数（让运营看到"售后压力"）
- **`judge()` 不动** —— 判定仍然只看 `neg_rate` ✅

## 5. 这条决定要复述一遍（防止以后被"优化"掉）

```text
"为什么不把 refund_rate 加进判定？"
   ↓
**因为它在这份数据里和差评率无关（52.5% 同向，≈随机）** ✅
   ↓
什么时候可以加：
   一旦 mock 里加上"退款和差评的耦合"（数据改动单 ⚠️），
   或者接了**真实平台数据**（真实数据里退款和差评当然相关 ✅）
   → 那时重跑 `scripts/probe_refund_corr.py`，
     同向率 > 75% 就可以加进判定 ✅
   ↓
**判断依据是那个脚本，不是谁觉得"应该加"** ✅
```

## 6. 验收

```powershell
python -m scripts.probe_refund_corr     # 应输出「21/40 同向 → 弱相关 → 只作展示」
python -m hub.cli retro                 # 4 组结论仍正确（判定没动 ✅）
python tests\check_retro_metrics.py     # 新测试：refund_rate 只展示、不影响判定
```
