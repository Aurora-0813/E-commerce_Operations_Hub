# 15 · LangGraph 对照实测（阶段 3.3）

> 目的：JD 要 LangGraph ✅，但形态 ③ 的流程是"固定 3 步取证 + 1 次判断"，
> **图框架的价值（路由 / 环 / 状态机）在这里用不上** ✅
> → 只写图版本 = "为了关键词而用"，会被问穿 ✅
> → 写两份 + 给对比数据，才能说清"我知道它解决什么问题、也知道这里不需要" ✅
>
> 实测：2026-10-31 ｜ langgraph **1.2.17** ｜ 模型 qwen2.5:7b ｜ 22 个簇

---

## 1. 两版的差异被**刻意限制在编排**

| | A 手写（`hub/agent/handle.py`） | B LangGraph（`hub/agent/graph.py`） |
| --- | --- | --- |
| 取证 | 顺序调用 + `try/except` | 3 个节点 + 边 |
| 判断 | 一次 `llm.chat` + 解析 + 校验 | `n_judge` 节点（**同一套 prompt/校验**） |
| 状态 | 局部变量 + `HandleResult` 对象 | `GState`（TypedDict）+ 同一个 `HandleResult` 对象 |
| 工具函数 | `hub/tools/readonly.py` 的 5 个 | **完全同一批函数** ✅ |
| 规则块 | `_rule_block()` | **同一个函数** ✅ |
| 返回结构 | `HandleResult` | **同一个** ✅ |

**为什么不把差异扩大**：如果 B 换了 prompt 或校验逻辑，对比就不公平了 ✅
（那样比的是"两种写法"，不是"两种编排"）

---

## 2. 实测数据（22 个簇，同一批、同一模型）

### 2.1 结果一致性（**最重要的指标**）

```text
结果一致：22/22（100%）　✅ 两版行为等价
```

**逐簇对比**：22 个簇的工具选择**全部相同**（含 14 个 `review.draft_reply`、
8 个 `listing.update_desc`）✅

**这一条的意义**：

```text
两版等价 → 后面所有差异（耗时/行数/可调试性）都**只来自编排方式** ✅
如果不等价 → 说明有一版写错了（我们真的踩到了，见 §4 ✅）
```

### 2.2 耗时

```text
A 手写 68.2s　B LangGraph 65.7s　（B 比 A 快 4%）
```

**这个数字不能当结论** ✅：

```text
单次 LLM 调用的波动是 2.8s ~ 7.5s（见 14 号文档）✅
22 个簇的总耗时 ≈ 66s，其中 99.9% 是 LLM
   ↓
4% 的差异（约 2.5s）**完全在噪声内** ✅
   ↓
**图的开销（节点调度）在毫秒级 —— 和 LLM 的秒级波动不是一个量级** ✅
   ↓
所以正确说法是："**两个版本在耗时上没有可测差异**" ✅
（说"图更快"是拿噪声编故事 ✅ ✗）
```

### 2.3 代码行数（**还债后的公平对比**）

```text
A 手写 377 行　B LangGraph 177 行（B 是 A 的 47%）
```

**这个对比是公平的**（2026-10-31 还债之后）：

| 之前的不公平 | 现在 |
| --- | --- |
| B 的 `n_judge()` 复制了 A 的判据（60 行） | **抽成 `judge_step()`，两版共用** ✅ → B 少了 68 行 |
| A 含 `save()`（约 35 行），B 没有 | 仍在 → 公平对比是 **342 vs 177（B 是 52%）** |

**但"B 更短"的原因不是"用了图"** ✅：

```text
A 的 `handle()`：**一个函数**干完 3 步取证 + 组装 evidence + 调判据
B 的图：        **3 个 10~20 行的小节点** + 4 条边
   ↓
B 短是因为**"拆得细"**，不是因为图 ✅
   ↓
手写版同样可以拆成 3 个小函数（`gather_cluster/reviews/history`）——
那样也会变短，而且**不需要 LangGraph** ✅
   ↓
**所以行数不能用来证明"图更好"** ✅
```

**真正能说明问题的是**：同样的拆分粒度下，**图多出来的东西是什么** ✅

```text
如果两边都拆成 3 个取证函数：
   A 手写：3 个函数 + 一个 `if/else` 串联 + 调 judge_step
   B 图：  3 个函数 + 4 条 `add_edge` + 调 judge_step
   ↓
多出来的就是：
   · `GState` 的 TypedDict 声明（约 10 行）
   · `build()` 里建图/编译（约 15 行）
   · **以及一个隐式契约：节点 return 什么、框架就并什么**（见 §4.1 的坑 ✅）
   ↓
**在图不带来能力的地方，成本就是"多一层声明 + 一层隐式契约"** ✅
```

## 3. 图版本**真的用了**一个图特性（不是摆样子）

```python
g.add_conditional_edges("history", _after_gather, {"judge": "judge", END: END})
   ↓
取证阶段任何一步失败 → 直接 END，**不浪费一次 LLM 调用** ✅
   ↓
手写版是靠 try/except 实现的 ✅
   ↓
**所以这不是"包了个壳"，是"用图的边表达了同一条控制流"** ✅
```

**但也要诚实**：这条控制流**用 `if` 也能表达**（手写版就是）✅ ——
图的价值在于**当控制流复杂到 `if` 表达不了时**才体现 ✅

## 4. 踩的坑（**这一节最有说服力**）

### 4.1 `topic` 靠 state 合并传递 → 丢了 → 选错工具

```text
第一次对照：A 选 review.draft_reply，B 选 listing.update_desc → 0/2 一致 ✅ ✗
   ↓
诊断：对照脚本里加了"送进模型的 prompt 长度"对比 ✅
   A=624　B=292　**差 332 字**
   ↓
332 ≈ 规则块的长度 ✅
   ↓
根因：`n_cluster` 里 `return {"topic": ...}` → 期望 LangGraph 合并进 state
      → **实际没传到 `n_judge`** ✅ → `_rule_block("")` → 规则块是空的 ✅
   ↓
后果：图版本的行为和无规则组一模一样（22/22 选 update_desc ✅）
   ↓
修法：**topic 存到 `HandleResult` 对象上，不靠 state 合并** ✅
```

### 4.2 还有一个真 bug（顺手查出来的）

```python
# graph.py 的 _wrap() 原来写的：
CallContext(role="operator", trace_id=res.steps[0].args.get("trace", ""))
                                            ↑ 第一次调用时 steps 是空的
   ↓
IndexError → 被 except 吞成"工具失败" → 会**静默跳过整个取证** ✅ ✗
   ↓
修法：trace_id 由调用方显式传入 ✅
```

### 4.3 这两个坑说明什么

```text
同一个 bug 在两版里的表现完全不同：
   A 手写版：不存在这个 bug（topic 是局部变量，一路传下去 ✅）
   B 图版：  topic 靠 state 合并 → 丢了 ✅ ✗
   ↓
而且**如果只写图版本，这个 bug 会表现为"agent 偶尔选错工具"** ✅
   极难查（prompt 里到底有没有规则，不打印就看不见 ✅）
   ↓
**这就是"两份实现互相验证"的价值** ✅
```

## 5. 结论：什么时候该用图，什么时候不该

### 5.1 这个项目里的判断

```text
形态 ③ 的流程：固定 3 步取证 + 1 次判断，无环、无复杂分支
   ↓
**用图：没有收益** ✅
   · 耗时无可测差异（噪声内）
   · 代码行数没有优势（且引入了重复代码）
   · **多了一层隐式契约**（state 合并）→ 反而多了一个坑
   ↓
**不用图：手写更直接** ✅
   · 状态是局部变量，读代码就知道数据怎么流 ✅
   · 调试时下断点、print，都在一个函数里 ✅
```

### 5.2 什么时候图**确实**更好

| 场景 | 为什么 |
| --- | --- |
| **有环**（如 ReAct 的"想→做→看→再想"） | 手写循环会变成嵌套 `while` + 状态机；图的边直观 ✅ |
| **条件分支多**（3 个以上路由） | `if/elif` 会嵌套；`add_conditional_edges` 是声明式的 ✅ |
| **需要 checkpointer**（中断后恢复、HITL 暂停续跑） | 这是 LangGraph 的原生能力，手写要自己造 ✅ |
| **多 agent 协作**（节点间共享复杂状态） | state 的 reducer 机制确实省事 ✅ |

**而我们形态 ③ 一条都不占** ✅

### 5.3 所以两份实现怎么处理

```text
保留两份 ✅（用户明确要求"形态不能删"）
   ↓
但定位不同：
   · `handle.py`（手写）= **生产主路径**（简单、可调试）
   · `graph.py`（LangGraph）= **对照实现 + 能力证明**
     → 用来回答"图能做什么、这里为什么不需要"
     → 也用来验证"手写版的行为是对的"（22/22 等价 ✅）
   ↓
**这比"生产用图，但图没带来任何好处"诚实** ✅
```

**第 1 条是这次对照暴露出来的真债**，而且它还教了一件事：

```text
"两份实现"最容易付的代价是【判据复制】✅
   ↓
复制之后，两份会**慢慢分叉** → 而"22/22 等价"这个核心结论就自动失效 ✅
   ↓
**所以写两份不是为了"秀"，前提是"共用同一份判据"** ✅
   （否则对比的是"两套不同的规则"，不是"两种编排" ✅）
```
