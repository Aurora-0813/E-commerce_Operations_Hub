## 4. 实现思路

### 4.1 M11 业务数据面（先做，M4 的命根子）

**为什么必须先做**：M4 的价格背离要价格、销量预测要销量、优先级 reach 要 GMV/UV。数据面缺了，M4 就是空转。

### 4.2 跨平台聚类（clustering.py）

**两步走，先兜底后升级**：

```text
第一步（P0，先做）：封闭枚举分桶
  按 root_cause(8类) × platform 直接分桶 → 每桶一个"簇"
  优点：可解释、零依赖、立刻能出结果
第二步（P1，后补）：embedding 聚类
  bge-small-zh 编码文本 → HDBSCAN → 簇命名(LLM)
  跨平台对齐：簇名向量余弦 ≥0.82 且业务域相同 → 合并为同一问题簇
```

**趋势**：与上一次 Run 同簇计数比较，`growth_rate = (n_now - n_prev)/max(n_prev,1)`。

**设计决策**：先用封闭枚举分桶，不是偷懒——它保证"聚类可解释、可复现"。HDBSCAN 调参不稳时，分桶就是兜底（对应设计文档降级矩阵）。

### 4.3 价格背离检测（pricing.py）

**问题**：同款在 A 平台比 B 平台贵很多，且 A 平台差评更多——这是"高价低质"信号。

```text
dev   = ln(price_p / median(同款跨平台价格))     # 中位数抗异常，不用均值
sev   = 该 SPU 差评率分位
flag  = |dev| >= 0.15 且 sev >= 0.70
score = 100 * sigmoid(4*(|dev|-0.15)) * (0.5 + 0.5*sev)
```

**三条要点**：

1. **基准用中位数**：同款跨平台价差极大时，均值会被带偏；
2. **促销豁免**：大促期间不判（配置 `promo_dates`），否则全是假异常；
3. **可比性分级**：只有 `COMPARABLE` 的指标才做差，`INCOMPARABLE` 禁止跨平台比较（设计文档口径映射，面试加分点）。

### 4.4 优先级排序（priority.py）

```text
P = 100 * (0.40*reach + 0.30*severity + 0.20*trend + 0.10*actionability)
```

| 因子 | 来源 | 说明 |
| --- | --- | --- |
| reach | M11 | 影响面（GMV/UV），无数据走 fallback |
| severity | 差评率分位 + 多模态严重度 | 问题多严重 |
| trend | growth_rate → sigmoid | 是否在恶化 |
| actionability | 有无可执行工具 | 有自动工具=1.0，需 HITL=0.6，无=0.2 |

**分档**：P≥80 → P0（4h 人工）、60–80 → P1（24h）、40–60 → P2、<40 → P3。


**关键约束**：`predict()` **永不抛异常、永远有返回值**（最差返回基线值 + 低置信 + 原因）。

**四层降级**（做不出也能交付的保险）：

| 层 | 触发 | 行为 | 输出 |
| --- | --- | --- | --- |
| L1 任务级 | 历史 < 60 天 | 改做波动检测（同比/分位数/STL） | `mode=sales_anomaly` |
| L2 实现级 | 依赖缺失/拟合失败 | 链中剔除，降下一实现 | `method` 变化 |
| L3 结果级 | 预测越界/全 NaN | 回退基线 | `degraded=true, confidence=low` |
| L4 全局 | 全失败/mode=off | 只报事实（本周 vs 上周） | "未启用预测" |

**评估（比模型本身重要）**：按时间切最后 14 天 holdout（禁随机切），MAE/MAPE/sMAPE 分层（爆款/长尾）；**必须与 `seasonal_naive` 对比，跑不赢就默认用基线**。

**判断边界**：LLM 不做数值预测（会幻觉、不可复现、贵），只解释预测结果。

### 4.6 Case RAG（案例检索增强）

**为什么**：生成动作建议时，LLM 内化知识不稳定、过时、会编。建议需要"历史案例"作为依据——这是本项目唯一的 RAG 场景，且**有 ground truth（DID 结论）**。

```text
问题簇 → 代表文本 → embedding → 召回(top-50)
       → 过滤(业务域/平台/结论明确) → 重排(top-3~5)
       → 注入建议 prompt → LLM 基于案例给建议
       → cited_cases 必须来自检索结果（防编造）
```

**三条铁律**：

1. `cited_cases` 只能引用检索返回的 case_id，否则 `CASE_NOT_GROUNDED`；
2. 检索为空 → `no_history=true` + 保守建议，**禁止虚构案例**；
3. POSITIVE 是"该怎么做"，NEGATIVE 是"别这么做"，两者都保留。

**评估**：recall@5（留出 20% 案例）、推荐采纳率、建议-复盘一致率。

**降级**：向量检索不可用 → 业务域+根因倒排规则匹配，永不阻塞建议生成。

## 8. 常见坑

1. **价格背离没做同款对齐**：拿不同商品比价格，全是假异常。**必须先 M11 主数据对齐，再谈背离**；
2. **基准用均值**：一个极端高价就把均值带飞，**用中位数**；
3. **大促没豁免**：双十一期间"价格偏离"是正常的，不豁免就输出一堆垃圾告警；
4. **reach 用假数据冒充**：无销量数据时悄悄用评价量算 reach，让优先级看起来"真实"。**必须标 fallback**；
5. **聚类直接上 HDBSCAN**：调参不稳就卡死。**先封闭枚举分桶，能出结果再说升级**；
6. **预测跑不赢基线还硬上**：模型比 `seasonal_naive` 差还坚持用，面试一问就崩。**跑不赢就用基线，这是加分不是减分**；
7. **Case RAG 允许编造引用**：模型引用一个不存在的案例，等于又开了一个幻觉口子。**cited_cases 必须落地校验**。

## 第二阶段：五维度扩展（评价 → 六维度）

> 属于 M4 分析层的横向扩展，纯加法，不动已有聚类 / 背离 / 优先级。

**新增 5 个 Detector + 4 个 Adapter**：

| 维度 | Detector | 分析方式 |
| --- | --- | --- |
| 订单 | `order_refund` | 规则 + 孤立森林（退款归因） |
| 发货 | `shipment_delay` | 规则（时效监控 + 延迟预警） |
| 到账 | `payment_recon` | 纯规则（对账，**不用 LLM**） |
| 投放 | `ad_roi` | 指标归因 + LLM 建议 |
| 商品 | `product_profit` | 规则算毛利 + LLM 建议 |

**数据面扩展**：`sales_daily` 加 `profit_margin`；新增 `shipment_daily / payment_daily / ad_daily` 三张表；新增 4 个 Adapter（订单/发货/到账/投放，复用现有基类）。

**按维度路由**：analysis 层按 `data_type` 分发——语义类（评价/投放/商品）走 LLM，数值类（订单/发货/到账）走规则，AI 只兜底低置信。**对账零幻觉是硬约束**。

**开发步骤**：加 4 个 Adapter（4h）→ 加 5 个 Detector（8h）→ 数据面字段/表（3h）→ 按维度路由 + 决策卡模板（3h）。

**验收**：每个维度产出决策卡；数值类维度不调 LLM；新增维度不改主流程。
