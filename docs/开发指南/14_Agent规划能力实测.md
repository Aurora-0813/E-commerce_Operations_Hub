# 14 · Agent 规划能力实测（阶段 1.3）

> 目的：**在做 agent 之前，先用数据决定它的形态**。
> 不是在"完整 / 半开放 / 受限"之间凭感觉选，而是先测出来。
>
> 实测日期：2026-10-31 ｜ 模型：qwen2.5:7b（本地 Ollama /v1） ｜ 工具：5 个模拟只读工具
> 脚本：`backend/scripts/probe_planning.py`

```text
如果直接做"完整 agent"（LLM 自由规划）：

   → 花 2 天，得出"7B 好像不太行"的模糊结论
   ↓
现在花 2 小时，得到【具体的失败模式】：

   ↓
而这两条都有对应的工程手段 ✅
```

## 2. 指标：**第一版设计错了，这里记录改了什么**

### v1（错）

```text
"首步正确率" = 第一步调用的工具是否等于 TOOL_BY_TOPIC[topic]
   ↓
实测结果 0% —— 因为模型第一步都在调 query_cluster（查这个簇是什么）
   ↓
**但那是正确的行为**：不查清楚怎么决定做什么？
   ↓
根因：`TOOL_BY_TOPIC` 表达的是"**最终**该做哪个写动作"，
      不是"第一步该查什么" —— 拿它去比第一步，指标本身就是错的 ✅
```

### v2（现在用的）

| 指标 | 定义 | 为什么这个才对 |
| --- | --- | --- |
| **首步只读率** | 第一步是只读查询（不是直接动手） | 不查清就动手 = 危险 |
| **收尾率** | ≤5 步内给出结论（`done`）或调了终态工具 | **"知道什么时候够了"才是 agent 的真本事** |
| **参数幻觉** | ID 类参数（spu_id / proposal_id / cluster_id）不是像 ID 的串，或与给定值不符 | 参数瞎填比选错工具更严重 |
| **上下文** | 平均每步 prompt 字符数 | 判断会不会撑爆 8k |

## 4. 失败模式分类（这是本报告的核心）

### 模式 A：**不会收敛**（收尾率 0%）

```text
行为：query_cluster → query_reviews → query_history → query_product → query_outcome
     把 5 个工具全查一遍，然后步数用尽
   ↓
它从不输出 {"done": true, "recommendation": ...}
   ↓
**不是"选错"，是"不知道什么时候停"** ✅
提示词里已经写了"信息够就收尾"（还加粗了），仍然 6/6 不收尾
```

### 模式 B：**参数不是取来的，是编的**（6/6）

三种表现，按严重程度排：

| 表现 | 例子 | 为什么严重 |
| --- | --- | --- |
| **占位词当参数** | `spu_id='待定'` / `'目标商品ID'` / `'需要具体商品ID'` | 它知道"这里该放个 ID"，但**没有去取** |
| **自己拼 ID** | `proposal_id='desc_update_2adf0897-…'` / `'描述修改'` | 它**发明了格式**，看起来很像真的 |
| **抄错 UUID** | 给定 `…94608f` → 抄成 `…98608f`；给定 `…1353de6` → 抄成 `…353de6` | **36 位十六进制它抄不准** |

**第三种最值得记**：

```text
这不是"幻觉"（它没有编造内容），是【能力边界】——
LLM 不适合当数据搬运工 ✅
   ↓
所以 agent 设计的第一条铁律：
   **任何 ID / 数字，都不许模型抄 —— 必须由代码从上下文注入** ✅
```

## 5. 结论与对策

### 判定：**③ 受限 agent**（固定步骤，LLM 只填参数）

**依据**（不是感觉）：收尾率 0% < 50%（判定门槛写在脚本里，测试前就定好了 ✅）

### 三条设计原则（直接由失败模式推出）

| 失败模式 | 对策 |
| --- | --- |
| A 不收尾 | **步骤由代码固定**：查簇 → 查评价 → 查历史 → 出建议。不再问"下一步做什么" |
| B 参数编造 | **参数由代码注入**：spu_id 从 `cluster.spu_ids` 取、proposal_id 从上一步结果取。模型**只看、不填** |
| A+B 共同 | **模型只做一件事**：给定证据，判断"支持什么建议" ✅ |

### 而这也解释了为什么"形态 ③"不是妥协

```text
能力（会按合理顺序调工具、认识工具、上下文够用）→ 保留 ✅
短板（不收敛、参数抄不准）                      → 用代码补 ✅
   ↓
**这比"让 7B 硬做完整 agent"更诚实，也更可靠** ✅
```

## 8. 形态 ③ 真机跑通后的两个发现（2026-10-31，`hub handle`）

### 发现 1：**证据编排有效，模型真的在用证据**

```text
第一次真机跑（簇「掉色严重」，123 条）：
   轨迹：query_cluster(6ms) → query_reviews(4ms) → query_history(8ms) → llm.judge(7637ms)
   证据：E1（簇概况）+ E2~E6（评价原文）+ E-H×2（历史战绩）
   校验：**引用了 2 条证据，有效 2 条** → **7B 这次没编引用** ✅
   ↓
前 3 步总共 18ms，全部成本在第 4 步的 7.6 秒 ✅
→ **"步骤代码化"不只是可靠性，也把成本压到了必须的一处** ✅
```

### 发现 2：**不给业务规则，模型会按"常识"选错**（重要）

```text
第一次跑：模型建议 **"更新产品描述，强调掉色问题"** → `listing.update_desc`
   ↓
而 `TOOL_BY_TOPIC["quality"]` 是 `review.draft_reply`，
代码注释写着理由："面料扎人/开线/起球是真质量问题，改详情页描述是粉饰，不解决问题"
   ↓
**"在详情页强调掉色" = 提前告诉买家会掉色，不是解决掉色** ✅ ✗
```

**这不是模型笨，是我们没把业务判断告诉它**：

| 修法 | 为什么这么改 |
| --- | --- |
| ❌ 在 prompt 里写"质量问题请选 review.draft_reply" | 那是**把答案喂进去**，agent 成了摆设 |
| ✅ **把规则作为"约束"注入 + 允许它不同意但必须说理由** | 规则是**业务方的人工判断**，模型是**常识判断**；两者不一致时应该**让人看见**，而不是悄悄发生 |

**注入后的效果（同一簇、同一模型、同 prompt 结构）**：

| | 建议 | 动作 | E-RULE |
| --- | --- | --- | --- |
| 注入前 | 更新产品描述，强调掉色问题 | `listing.update_desc` ✗ | （无此字段） |
| **注入后** | **回复差评并反馈内部** | **`review.draft_reply`** ✅ | **与业务规则一致** ✅ |

**而且它仍然引用了 2 条有效证据** ✅ —— 说明"给规则"没有让它放弃依据 ✅

### 由此得到的第三条设计原则

```text
原则 ③：**业务规则要显式告诉模型，并且分歧要被记录**
   ↓
实现：`handle.py::_rule_block(topic)` 只给这个 topic 的那一条规则
      （给整张表会让模型把别的类型的规则串过来 ✅）
      并要求输出 `follows_rule` / `why_not_rule`
      结果里统一记一条 `E-RULE`：一致 / 不一致（附理由）/ 无规则
   ↓
**分歧时状态仍是 DONE** —— 分歧不是错误，是"值得人看"的信号 ✅
（如果分歧就拦下，人工会被淹没在"AI 不同意"的噪音里 ✅）
```

### 和 `proposer` 的关系（两者并存，不是替代）

```text
proposer（确定性）→ 按规则选工具、生成提案、走网关审批
agent（判断性）  → 按证据选工具、给"依据 + 建议"、可采纳成提案
   ↓
**两者结果的差异本身是有价值的信号**：
   总同意 → agent 没提供新信息
   总不同意 → 要么规则错了，要么模型不行
   ↓
这个差异也是**轨迹评测**（阶段 3.5）要量的东西之一 ✅
```

## 9. 轨迹评测：**有规则 vs 无规则**（2026-10-31，阶段 3.5）

### 9.1 为什么要做对照组（第一次差点得出错误结论）

```text
先只跑了"有规则"那组：一致率 3/3 = 100%
   ↓
脚本当时打印："分歧率 0% → **agent 没有提供新信息**" ✅
   ↓
**这个结论是错的** —— 因为规则是**我们自己写进 prompt 的** ✅
   测到的是"它听不听话"，不是"它会不会判断" ✅
   ↓
就像考试把答案印在卷子上，然后说"这学生全会" ✅
   ↓
→ 必须加一组"**不给规则**"的对照，测**模型自己的判断** ✅
```

### 9.2 实测数据（全量 22 个簇，同一模型、同一 prompt 结构）

| 指标 | **A 有规则** | **B 无规则** |
| --- | --- | --- |
| 与规则一致 | **22/22（100%）** | **8/22（36%）** |
| 分歧率 | 0% | 64% |
| 引用编造 | 0 / 74 | 0 / 63 |
| 模型步平均耗时 | 3260ms | 3025ms |
| 只读步平均耗时 | 3ms | 3ms |

**但真正要看的是 B 组"选了哪个工具"的分布**（这才是 9.3 的核心发现）：

| B 组的实际选择 | 次数 |
| --- | --- |
| `review.draft_reply` | **0** |
| `listing.update_desc` | **22** |
| `hitl.create` | 0 |

**22 个簇、6 种问题类型（quality / size / desc_mismatch / logistics / service / misship），
模型无一例外全选 `listing.update_desc`** ✅

（前 3 个簇的初测也是这样：2/2 选 update_desc —— 当时样本小，我误读成"分歧 67%"，
全量才看清是"固定选一个" ✅ —— **这就是为什么要跑全量** ✅）

### 9.3 三个结论（都有数据支撑）

```text
① **无规则时，模型 22/22 全选同一个工具** ✅ ← 这是最重要的发现
   → 不是"判断和规则不一致"，是**根本没有在判断** ✅
   → 证据：14 个"规则是 draft_reply"的簇，它全选 update_desc；
           另外 8 个"规则本来就是 update_desc"的簇，它也选 update_desc
           → **统一 22/22 选 update_desc** ✅ ✗
   → 最荒谬的一个：「客服态度差」→ 建议改详情页描述（毫无关系 ✅）
   → **结论：7B 在无规则约束时，工具选择能力接近于零** ✅

② **有规则时 22/22 一致** ✅
   → 规则的注入是有效的（模型会遵守 ✅）
   → 但注意：这测的是"它会不会听话"，不是"它会不会判断" ✅
   → 结合 ① 就清楚了：**规则是决策的唯一来源，模型只负责组织语言** ✅

③ **引用编造 0/137**（A 组 74 + B 组 63）✅
   → 在"给了明确证据编号"的前提下，7B 一次都没编引用 ✅
   → 说明 `E1..En` 编号 + 校验这个设计有效 ✅
   （对比：M3 早期没有编号时 grounded 只有 87.5%）
```

### 9.3.1 补测：模型是"选工具"还是"写建议后硬凑工具"？

```text
背景：B 组（无规则）22/22 全选 listing.update_desc，但当时没记建议原文 ✅
   ↓
补上原文后跑了一次，验证假设："是不是先写泛化建议、再挑最像的工具？"
```

**判据与结果**：

| 指标 | 结果 |
| --- | --- |
| 建议里提到「描述/详情页/说明」的 | **20/22（91%）** |
| 实际选了 `listing.update_desc` 的 | **22/22（100%）** |
| 两者重合 | **20/20（100%）** |

**那 2 条"不重合"的，反而揭示了机制**：

| 簇 | 模型的建议 | 选的工具 |
| --- | --- | --- |
| 客服态度差 | **更新客服培训手册**，强调响应时间 | `listing.update_desc` ✗ |
| 物流延迟 | **更新物流信息模板** | `listing.update_desc` ✗ |

```text
"更新客服培训手册" / "更新物流信息模板" —— 系统里**根本没有这两种工具** ✅
   ↓
但它还是选了 `listing.update_desc` ✅
   ↓
因为 **`update_desc` 是唯一名字里带"更新/改"的工具** ✅
   ↓
**结论：它不是"选择工具"，是"先写一句『更新 XX』，再挑最像的工具硬凑"** ✅
```

### 9.3.2 而且它的建议本身大多没有业务意义

```text
· 掉色严重   → "在详情页强调洗涤注意事项"      ← 提前告诉买家会掉色，不解决问题
· 漏发少赠品 → "在描述里说明赠品政策"          ← 赠品漏发是**履约问题**，不是描述问题
· 物流延迟   → "在详情页强调物流速度"          ← 物流慢是**履约问题**，写描述没用
· 客服态度差 → "更新客服培训手册"              ← 培训手册不是商品描述
   ↓
**全都是"在文案上做文章"，而不是"解决实际问题"** ✅
   ↓
这才是 7B 的真实水平：
   **它会写通顺的句子，但不会做业务判断** ✅
```

### 9.3.3 所以架构上的结论（比"分歧 64%"更强）

```text
❌ 弱结论："规则把判断拉回来了 64%"
   （暗示模型有判断，只是和规则不同）

✅ 强结论：
   "无规则时，模型 **22/22 全选同一个工具**，
    且**先写建议再硬凑工具**（连'更新客服培训手册'都硬凑到 update_desc）；
    建议本身也大多是'在文案上做文章'，不解决实际履约/质量问题。
    → 它在'选工具'和'判断业务该怎么处理'这两件事上**都没有能力**。
    → 规则不是'纠偏'，是**决策的唯一来源**；
      模型的作用只剩：把证据组织成人能读的句子 ✅"
```

### 9.4 这组数据回答了一个更根本的问题

```text
"为什么要用规则，而不是让 LLM 自己判断？"
   ↓
之前只能讲道理："LLM 缺少业务上下文，规则更可靠" —— 听起来像借口 ✅
   ↓
现在有数据（22 个簇）：
   · 不给规则 → **22/22 全选同一個工具**（连"客服态度差"都建议改详情页）
   · 给规则   → 22/22 一致
   ↓
所以问题不是"LLM 判断得准不准"，而是：
   **它在"选工具"这件事上根本没有能力，只会固定选一个** ✅
   ↓
**规则不是"纠偏"，是"决策的唯一来源"** ✅
模型的作用缩小为：把证据组织成人能读的建议（这一步它做得不错 ✅）
   ↓
**这才是能放进简历/面试的东西** ✅
```

### 9.5 局限（别把方向性证据当比率）

| 局限 | 影响 |
| --- | --- |
| **只测了 7B** | 更大模型/云端会不会也"固定选一个"未知 → **已补测，见 §10（结论被修正）** ✅ |
| **B 组没记建议原文** | "为什么全选 update_desc"只能推测（见 9.3.1） |
| 只有 22 个簇 | 6 种类型各 2~4 个，够看方向，不够算类型级比率 |
| 只测了工具选择 | 没测"建议内容的质量"（那需要人工评，或 Judge —— 我们明确不做 Judge ✅） |

**补测成本（如果要做）**：换云端模型跑同一个脚本 → 只改 `.env` 三行 ✅ 约 3 分钟 ✅
**（已做：见 §10。代价是"云端一次 30 秒"，实际花了约 5 分钟才跑完 5 个 ✅）**

## 10 · 跨量级对照：7B 本地 vs qwen-max 云端（2026-10-31）

### 10.1 数据（同 5 个簇、同 prompt 结构、都不给规则）

| 簇 | 类型 | 业务规则 | **7B（本地）** | **qwen-max（云端）** |
| --- | --- | --- | --- | --- |
| 掉色严重 | quality P0 | review.draft_reply | update_desc ✗ | **hitl.create** ✗ |
| 起球严重 | quality P0 | review.draft_reply | update_desc ✗ | **hitl.create** ✗ |
| 尺码偏大 | size P1 | listing.update_desc | update_desc ✅ | update_desc ✅ |
| 图片与实物不符 | desc_mismatch P1 | listing.update_desc | update_desc ✅ | update_desc ✅ |
| 客服态度差 | service P1 | review.draft_reply | update_desc ✗ | **hitl.create** ✗ |
| **与规则一致** | | | **2/5（40%）** | **2/5（40%）** |
| 引用编造 | | | 0 | **0 / 30** |
| 模型步耗时 | | | **~3 秒** | **23~38 秒** |

### 10.2 但"一致率相同"是假象 —— 两者的**失效方式完全不同**

```text
7B：**22/22 全选同一个工具**（update_desc）✅
    → 它不是"判断错了"，是**没有在判断** ✅
    → 一个永远选同一个东西的系统，不叫判断 ✅

qwen-max：**按「这个问题该谁处理」来选** ✅
    · 需要核查批次/供应商/客服记录的（质量缺陷、客服态度）→ **hitl.create（转人工）**
    · 只是信息没写清的（尺码、图片）                  → **listing.update_desc（改描述）**
    → **这个判断很专业，而且比我们的规则更细** ✅
```

### 10.3 所以必须修正 §9 的结论

```text
❌ §9 写的："规则是决策的唯一来源，模型只负责组织语言"
   ↓
**这个结论只在 7B 上成立** ✅
   ↓
✅ 准确的结论：
   "**规则的价值随模型能力变化**：
     · 对 7B（无判断能力）→ 规则是**唯一的决策来源**
     · 对 qwen-max（有判断能力）→ 规则是**参考**，
       模型能给出更细、甚至更谨慎的判断（P0 → 转人工而不是回复）
     → 所以'要不要把规则写死'**取决于用什么模型** —— 这才是完整结论 ✅"
```

### 10.4 而且 qwen-max 暴露了**我们规则本身的问题**

```text
我们的规则：quality → review.draft_reply（回复差评）
   ↓
但「掉色 123 条、P0、要核查染色批次」是**内部质量问题** ✅
   → 光回复买家解决不了 ✅
   → 模型说"转人工核查批次、评估下架/补偿" ✅ **更符合实际运营** ✅
   ↓
**所以我们那条规则在 quality 类上过于简化** ✅
   → 它把 quality 一刀切成"回复" ✅
   → 而真实运营要区分"该回复" vs "该核查" ✅
   ↓
**这是"规则注入"这种方法本身的局限** ✅：
   规则是**离散的映射**（类型 → 工具）✅
   而现实是**连续的判断**（严重度 × 类型 × 是否内部问题）✅
```

### 10.5 云端不能直接上生产（实测）

```text
模型步耗时：**23~38 秒/次**（7B 是 3 秒）✅
   ↓
全链 57 次 LLM 调用 → 约 **40 分钟**（本地 7 分钟）✅
   ↓
而且**会超时失败**（首次跑 22 个：2/6 个 `TimeoutError` / `WinError 10054`）✅
   ↓
**所以"云端更强"≠"云端能生产"** ✅
   → 用云端必须配：更长超时 + 重试 + 降级 ✅
   → 而这正是 M7 延迟队列 + 重试已经有的能力 ✅
   ↓
**结论**：云端适合"离线/异步/对延迟不敏感"的环节（如 brief、批量复盘）✅
         在线交互（agent 处理单个簇）仍应本地 7B ✅
```

### 10.6 引用质量：云端明显更好

```text
qwen-max：每条建议引用 **4~7 条**证据，**编造 0/30** ✅
7B：      每条建议引用 **2~3 条**，编造 0/74 ✅
   ↓
两者都不编造（编号机制有效 ✅）
但云端**用得更充分**（7 条 vs 2 条）✅
   → 说明它真的在"综合证据"，而不只是"挑一两条能用的" ✅
```

### 10.7 一句话总结

```text
"同一个任务，两种模型，两种失效方式：
  7B      → 不会判断（22/22 固定选一个）→ 靠规则兜住
  qwen-max → 会判断，但**慢**（30 秒）且**会超时** → 靠异步+重试兜住
  ↓
而且它反过来指出：**我们给 quality 定的规则太粗**。
  真正该做的是'按严重度 × 是否内部问题'分流，而不是'类型 → 工具'一刀切。
  ↓
这条比'我用了 LangGraph'值钱得多 —— 它是**用两个模型互相照出来的**。"
```

### 10.8 **为什么没做"同量级不同家族"对照**（不做也要写清 ✅）

路线图 §5.3 要求两组：同量级（7B 的不同家族：qwen2.5 / llama3.1 / glm-4-9b）+ 跨量级。

**实际只做了跨量级（7B vs qwen-max）** ✅

| 为什么不做 | 说明 |
| --- | --- |
| **没有第二个 7B 可跑** | 本机只装了 `qwen2.5:7b`；换家族要 `ollama pull llama3.1:8b`（约 4.7 GB 下载） |
| **收益不抵成本** | 它要回答的是"是不是**这个模型**特别笨"，而我们**已经从 v2 探针拿到了更强的证据**：收尾率 0%、参数幻觉 6/6 —— 这不是"某个模型笨"，是**7B 级别在"选工具+填参数"上普遍不可靠** |
| **已有一个反向对照** | 跨量级对照（qwen-max）**已经**说明"规模有用"：它会按类型选，还会更谨慎地转人工 ✅ 所以"要不要更大模型"这个问题**有答案了** |

**这条不做的影响**：

```text
❌ 不能断言"所有 7B 都不行"（只测了一个家族）
✅ 但"形态 ③ 的判定"**不受影响**：
   形态 ③ 的前提是"模型只做一次判断、参数由代码给" ✅
   而这个前提**无论哪个 7B 都更稳**（少一次选择 = 少一个失效点 ✅）
   ↓
**所以这条缺口的后果是"结论的适用范围变窄"，不是"结论错了"** ✅
```
