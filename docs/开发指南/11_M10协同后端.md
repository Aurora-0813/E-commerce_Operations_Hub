## 4. 实现思路

### 4.1 回复草稿闭环（reply.py）

**状态机**：

```text
DRAFT → PENDING_REVIEW → APPROVED → SENT → TRACKING → CLOSED
   │          │              │          │
   └──────────┴──────► REJECTED（任一环节拒绝即终止，留原因）
```

**四个环节**：

| 环节 | 实现 | 要点 |
| --- | --- | --- |
| 生成 | LLM 按模板 + 引用证据 | 复用 M3 的 `Evidence`，回复必须引用 ≥1 条评价 |
| 合规校验 | 关键词拦截 | 禁止"保证/一定/百分百/赔偿/退款承诺/私了" |
| 审批 | 走 M5 网关 | 发送是 L3，**必须** HITL，不审批不放行 |
| 发送 | 平台 API 回执 | 回执 ID 落库，供状态回查（复用 M6 的 E4） |

```python
class ReplyDraft(BaseModel):
    draft_id: str
    review_ids: list[str]
    content: str
    compliance_flags: list[str]     # 命中违禁词就非空
    status: Literal["DRAFT","PENDING_REVIEW","APPROVED","SENT","TRACKING","CLOSED","REJECTED"]

    @model_validator(mode="after")
    def no_promise_wording(self):
        banned = ("保证", "一定", "百分百", "赔偿", "退款承诺", "私了")
        if any(w in self.content for w in banned):
            raise ValueError("COMPLIANCE_BANNED_WORD")
        return self
```

### 4.2 通知 outbox（notify.py）

**为什么用 outbox**：业务事务里直接发通知，会出现"业务成功但通知失败"或"通知成功但事务回滚"。正确做法：**业务只写 outbox 表，异步派发**。

| 项 | 设计 |
| --- | --- |
| 幂等 | `notification` 唯一键 `(event_type, resource_id, channel, recipient)` |
| 合并 | 同类事件 10 分钟内合并摘要，防通知风暴 |
| 派发 | 每 5 分钟扫 outbox，重试 3 次（10s/60s/300s），仍失败进 DLQ |
| 渠道 | 企微 webhook / SMTP / 站内（P1 可先只落库不真发） |

**触发事件**（对应设计文档）：Run 完成含 P0 簇、L3 待审批、SLA 超时升级、复盘结论、DLQ 增长。

### 4.3 报表生成（report.py）

**合规边界（这是重点）**：报表只能包含**聚合值**，原文/PII/逐条明细永不进入。

```text
report_field_whitelist（白名单）：
  neg_rate / cluster_count / judge_avg / ...
  只有白名单字段可被报表引用，其余字段在渲染上下文里根本不存在
```

| 项 | 设计 |
| --- | --- |
| 白名单 | `report_field_whitelist` 表，只有聚合字段 |
| 行数上限 | `max_rows=5000`，超限要求缩小范围（防拖库） |
| 权限 | 导出需 `supervisor`，写审计 |
| 水印 | PDF 加"内部/租户/导出人/时间" |
| 生命周期 | 对象存储 7 天过期删除 |

**单测强制断言**：报表渲染上下文里不存在 `content_clean` / `image_sha256` / 手机号格式。

### 4.4 权限 / 租户 / 审计（auth.py）

| 项 | 设计 |
| --- | --- |
| 登录 | 本地账号（argon2）+ OIDC 单 IdP；JWT RS256 |
| 角色 | operator / supervisor / admin / analyst（RBAC） |
| 租户隔离 | 业务表带 `tenant_id`，**只从 token 取，忽略客户端传入**（防越权） |
| 审计 | `audit_log` 表，append-only（收回 UPDATE/DELETE 授权） |

**双重校验**：API 层验权限 + 网关层再验 scope（设计文档 §7.4 要求）。

### 4.5 知识沉淀（knowledge.py）

```text
knowledge_entry：type ∈ {playbook, faq, rule_candidate, prompt_patch}
状态机：DRAFT → IN_REVIEW → PUBLISHED → ARCHIVED
来源：POSITIVE 复盘结论 → playbook；人工确认的簇 → faq
发布：需 admin；rule_candidate 上线必须过 30 门禁
```

## 8. 常见坑

1. **通知在业务事务里直发**：事务回滚了通知还在，或通知失败拖垮业务。**outbox 表是标准解**；
2. **报表开了通用导出**：等于开放原始数据外带口。**白名单 + 行数上限 + 审计**；
3. **租户隔离靠"前端不显示"**：前端藏了但接口能查，等于没隔离。**后端强制注入 tenant_id**；
4. **审计表能 UPDATE/DELETE**：那审计日志可以改，等于没有。**append-only，收回写权限**；
5. **回复没走 L3 审批**：自动回复客户是高风险动作，绕过 HITL 就是合规事故。**发送必须 L3 + 审批**；
6. **违禁词只在生成时查**：审批后再改内容就绕过了。**审批通过时二次校验**。
