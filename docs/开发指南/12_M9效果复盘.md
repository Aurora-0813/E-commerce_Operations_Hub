# M9 效果复盘（DID）

> 读完这篇你应该能回答三个问题：
> 1. **怎么判断"这个动作到底有没有用"**——为什么不能只看"做之前 vs 做之后"；
> 2. **为什么有些结论必须是"说不清"**——撞大促、重叠干预、样本不够时，正确答案是 INCONCLUSIVE；
> 3. **一个做对了但仍然会被自己骗的地方**——样本量不足时，真实有效的动作也会被判"不显著"。
>
> 配套：`docs/开发指南/12`（本篇）、`hub/retro/`（代码）、`scripts/diagnose_did.py`（诊断）。

---

## 一、为什么不能只看"做之前 vs 做之后"

```text
"我们改了描述，两周后差评率从 30% 降到 19%，降了 11 个点，有效！"
   ↓
这句话错在哪：
   · 大促让买家更满意，差评率本来就会降
   · 换季、平台改规则、竞品缺货…… 任何一件都能造成 11 个点
   · 你还记得住"两周前正好在做什么"，但记不住"两周前还有什么在发生"
```

**DID（双重差分）做的就是减掉这些"别的原因"**：

```text
DID = （处理组：后 - 前） - （对照组：后 - 前）
        ↑ 动作带来的变化      ↑ 没做动作也会发生的变化
```

对照组 = **同期没被任何干预覆盖的商品**。它在"后窗口"的变化，
就是"如果不做动作，本来会怎样"的估计。

## 二、代码结构

| 文件 | 职责 | 关键设计 |
| --- | --- | --- |
| `hub/retro/metrics.py` | 按商品算 (评价数, 差评数) | **按商品聚合**，不是直接给比率——bootstrap 要按商品重抽样 |
| `hub/retro/did.py` | 点估计 + bootstrap + 判结论 | 逐商品差值（固定效应）、混杂优先于显著性 |
| `hub/retro/report.py` | 找到期动作 → 选对照 → 查混杂 → 写回 | 一个提案 = 一个复盘单元 |
| `hub/action/outcome.py` | 动作执行时登记观察窗口 | 一个受影响商品一条（配对需要） |

```text
动作执行（M5/M6）
   → 登记 action_outcome（前 14 天后 14 天，status=WAITING）
   → 窗口走完
   → hub retro：算 DID → 判结论 → 写回 status=DONE
```

## 三、四个必须知道的判断

### ① 混杂检查必须**排在**显著性之前

```text
G4（撞大促）的真实情况：
   处理组：24.39% → 11.36%（降 13 个点，看起来大获成功）
   DID = -6.13pp，区间 [-14.91, +3.61]
   ↓
如果只看显著性：区间跨 0 → 判"不显著" → **碰巧对了，但理由错了**
如果效应再强一点：区间不跨 0 → 判 POSITIVE → **完全错了**
   ↓
所以顺序必须是：
   数据缺失 → 对照组不足 → 重叠干预 → 撞大促 → 变化不显著 → POSITIVE/NEGATIVE
```

**"统计显著"不等于"因果成立"。** 一个混杂因素能让 DID 又大又显著。

### ② 大促要区分「全店」和「定向」

```text
全店大促（promo_calendar.spu_ids 为空）
   → 处理组和对照组都在促销里 → DID 能减掉 → **不是混杂**

定向促销（spu_ids 命中处理组）
   → 只有处理组的商品在做活动 → 对照组减不掉 → **是混杂**
```

**真实业务里"主推款才做大促"非常常见。** 数据里分不出来，只有日历能分出来。

> 踩坑记录：第一版写成"窗口内有任何促销就算撞大促"，
> 结果一个全店大促让 4 组全部判 INCONCLUSIVE，M9 等于没做。

### ③ bootstrap 必须按**商品**重抽样，不能按评价

```text
同一商品下的评价不独立（同一批面料出问题 → 差评成堆）
   ↓
按评价抽样 → 置信区间算得比真实窄 → 把"不显著"判成"显著"（假阳性）
   ↓
按商品（聚类）抽样 → 区间是诚实的
```

**这在统计上叫"聚类相关"**，是面板数据最常见的错误来源。

### ④ 估计量用「逐商品差值再平均」，不是「聚合比率之差」

```text
聚合：Σbad_after/Σn_after - Σbad_before/Σn_before
   ↓ 按评价数加权
一个 60% 差评率的商品会把它自己的异常放大到整组

逐商品差值：mean_i(rate_after_i - rate_before_i)
   ↓ 每个商品只贡献"自己的变化"，基期水平被自己抵消
这是面板 DID 的标准做法（单位固定效应），方差也小得多
```

**注意**：换成它是**口径正确**，不是为了让结果显著。
如果换了还是不显著，应该承认"这个数据测不出来"，而不是继续换公式。

## 四、预埋剧本：怎么验证 M9 是对的

**没有 ground truth 的复盘系统，等于自说自话。**
所以 mock 数据里**预埋了 4 组干预**（`data/mock/historical_interventions.csv`）：

| 组 | 真实效果 | M9 应该判 |
| --- | --- | --- |
| G1 | 改描述，差评率 ×0.55 | **POSITIVE** |
| G2 | 回复差评，×0.97（几乎无效） | INCONCLUSIVE「变化不显著」 |
| G3 | 回复话术不佳，×1.35（变差） | **NEGATIVE** |
| G4 | 改描述 ×0.55，但**同期定向大促** | INCONCLUSIVE「撞大促」 |

实测结果（2026-10-30）：

```text
G1  POSITIVE      DID -10.71pp  [-18.87, -2.45]   n=944
G2  INCONCLUSIVE  DID  +7.12pp  [-2.82, +16.44]   n=962（区间跨 0）
G3  NEGATIVE      DID +12.02pp  [+2.41, +22.47]   n=928
G4  INCONCLUSIVE  DID  -6.13pp  [-14.91, +3.61]   n=998（撞大促）
```

**4/4 与预埋答案一致。**

## 六、诚实局限（这一段比上面都重要）

### 局限 1：样本密度不够时，真实有效的动作也会被判"不显著"

```text
第一版 mock 每平台 2000 条评价
   ↓
DQE 洗掉 40% 刷单后，单个商品每 14 天窗口只剩 6~20 条
   ↓
`3/12 = 25%` 这种比率的标准误是 ±12 个百分点
   ↓
DID 的置信区间宽到 ±13pp
   ↓
**真实有效的 G1（降 45%）被判"不显著"**
   ↓
修法不是改公式，是把样本提到 3500 条/平台（每商品每窗口 ~23 条）
```

**这条教训值得单独记**：**代码正确 ≠ 结论能出来。**
样本量是**实验设计**的一部分，不是实现细节。

### 局限 2：DID 只能排除**已知的**混杂

```text
我们只查了：促销日历、重叠干预、数据缺失、样本量
   ↓
没查的：竞品缺货、平台规则变化、季节性、我们不知道的事
   ↓
所以结论的措辞是"相对对照组多降了 X 个百分点，且没有已知混杂"
   ↓
**不是"这个动作造成了 X"**
```

### 局限 3：一个商品被多个动作干预时，效果不可归因

```text
同一个商品可能同时落在两三个簇里，各出一个提案
   ↓
M9 检查到窗口重叠 → 判"重叠干预" → INCONCLUSIVE
   ↓
这是**正确的保守**，但也意味着：动作做多了反而谁都证明不了
   ↓
真实系统的做法是【排队执行】（一次只动一个），而不是同时上
```

### 局限 4：14/14 天窗口是约定，不是真理

```text
改描述的见效时间（几天）和回复差评的见效时间（下一波买家）不同
   ↓
统一用 14 天对两者都是妥协
   ↓
更严谨的做法：按动作类型配置窗口，并且做"提前一天/延后一天"的稳健性检验
```

**这些都没做，写在这里是为了不被当成"已经做完了"。**
