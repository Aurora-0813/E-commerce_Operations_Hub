## 第 1 步：工程骨架 + 配置 + 错误

### 目的

给整个项目打地基。后面要写 10 多个模块，如果没有统一的配置和错误处理，每个模块各写各的，很快就会乱成一团。

### 思路

**分层，并且只允许单向依赖：**

```text
业务模块 → contracts → core（不依赖任何东西）
```

`core` 放"每个模块都要用"的东西：
- `config.py`：全局配置（数据库地址、LLM 参数、降噪阈值……）
- `errors.py`：统一错误（`HubError` + 错误码表）

为什么放最底层：配置和错误是"基础设施"，不依赖任何业务，放最底层就不会出现循环依赖。

### 解决了什么问题

| 问题 | 不解决的后果 | 怎么解决 |
| --- | --- | --- |
| 配置散落各处 | 改数据库地址要全局搜索替换 | 集中到 `Settings`，用 `.env` 覆盖 |
| 错误格式不统一 | API 返回千奇百怪，无法程序化处理 | 统一 `HubError(code, message, retryable)` |
| 错误码硬编码 | 改错误码要全文替换 | 集中到 `ErrorCode` 类 |

### 数据流

```text
.env 文件 / 环境变量
   │  pydantic-settings 读取
   ▼
Settings（app / storage / llm / dqe / gateway 五个分组）
   │  业务代码 import
   ▼
各模块拿配置
```

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `pydantic.BaseModel` | 定义配置分组的数据模型 |
| `pydantic_settings.BaseSettings` | 支持从 `.env` / 环境变量读配置 |
| `SettingsConfigDict(env_prefix="HUB_", env_nested_delimiter="__")` | 定义环境变量命名规则 |

环境变量映射规则：`HUB_STORAGE__URL` → `settings.storage.url`（双下划线表示嵌套）。

### 踩的坑

无（第一次就验证通过）。验证命令：

```powershell
python -c "from hub.core.config import Settings; from hub.core.errors import HubError, ErrorCode; s = Settings(); print('env=', s.app.env, '| 错误码=', ErrorCode.HEADER_NOT_FOUND)"
```

## 第 2 步：契约层（7 个文件）

### 目的

定义**模块之间传数据的唯一标准**。比如"一条评价"长什么样、"一条归因结果"长什么样，先在这里定死，后面所有模块都照这个来。

### 思路：契约先行

传统做法是"先写功能，边写边定数据结构"，结果写到一半发现字段不对，到处改。我们的做法反过来：

```text
先定契约（数据结构）→ 再写实现 → 契约是唯一真相
```

好处：
1. 模块之间不传"裸 dict"，传有类型的对象；
2. 字段一改，所有用到的地方立刻报类型错误，不会漏；
3. 两个反幻觉机制能写成"构造时校验"，而不是"事后检查"。

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 模块间数据格式不一致 | 全部用 `Record` / `RawBatch` 等契约 |
| 模型输出"编造证据" | `Attribution.ground_evidence` 构造时校验 |
| Case RAG"编造案例" | `CaseAugmentedSuggestion.check_citations` 构造时校验 |
| 金额精度丢失 | 契约里金额字段用 `Decimal` |

### 契约分类（7 个文件）

| 文件 | 关键契约 | 服务于 |
| --- | --- | --- |
| `ingress.py` | `RawBatch` / `RawSheet` / `BadRow` / `Record` / `MappingReport` | 数据接入 |
| `quality.py` | `DQEVerdict` / `Validation` / `Violation` | DQE 降噪 |
| `analysis.py` | `Attribution` / `Evidence` / `IssueCluster` / `Anomaly` / `Priority` | 归因 + 分析 |
| `multimodal.py` | `VisionTags` | 多模态 |
| `gateway.py` | `ToolSpec` / `ToolCall` / `ToolResult` / `VerifyResult` / `RiskLevel` | 工具网关 |
| `retro.py` | `ActionOutcome` / `OutcomeEffect` | 效果复盘 |
| `case.py` | `CaseEntry` / `RetrievedCase` / `CaseAugmentedSuggestion` | Case RAG |

### 数据流（以 `Record` 为例）

```text
xlsx 一行
   │  适配器解析
   ▼
Record(
    platform="jd",              # 哪个平台
    rating=5,                   # 评分（归一后 1~5）
    fields={...},               # 业务字段（正文、标题、规格…）
    monetary={price: Decimal},  # 金额（Decimal）
    ts=2026-09-27 16:51,        # 业务时间
    impl="ingress.v1"           # 谁产出的（可追溯）
)
```

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `pydantic.BaseModel` | 契约基类 |
| `pydantic.Field(ge=, le=, min_length=, max_length=)` | 字段约束（评分 0~1、证据 4~80 字） |
| `pydantic.model_validator(mode="after")` | 构造后校验（反幻觉） |
| `pydantic.ValidationInfo` | 获取 `context`（原文内容） |

### 踩的坑（这段很值钱）

#### 坑 1：`model_validator` 拿不到 context（静默失效）

**现象**：合法的证据也被判定"不存在"，报 `EVIDENCE_NOT_GROUNDED`。

**原因**：Pydantic v2 里，`model_validator(mode="after")` 要拿到 `context`，函数参数**必须显式标注类型**：

```python
# ❌ 错误：拿不到 context，且不报错
@model_validator(mode="after")
def ground_evidence(self, info):
    ...

# ✅ 正确：必须写 info: ValidationInfo
@model_validator(mode="after")
def ground_evidence(self, info: ValidationInfo):
    ...
```

**教训**：Pydantic 的参数注入靠**类型注解**，漏了注解它不会报错，只是"悄悄不注入"——这是最危险的 bug 类型。

#### 坑 2：测试数据写错，反幻觉反而"抓对了"

**现象**：调试时真证据也被拒。

**原因**：我写的测试引用是 `"衣服开线了"`，但原文是 `"这件衣服破洞，还开线了"`——"衣服"和"开线了"中间隔着"破洞，还"，**不是连续的一句话**。

**结论**：**代码是对的，测试数据是错的**。反幻觉机制精确抓住了"模型拼凑假句子"的情况，这正是它的价值。

**教训**：
1. 遇到"看着对但结果不对"，加 `print(repr(...))` 调试，不要猜；
2. 测试用的"证据引用"必须从原文**逐字复制**，不能凭印象改写。

### 两个反幻觉机制（本步最核心的成果）

```text
1. 归因证据落地：
   模型说"因为原文里这句" → 系统核对"这句是否原文子串" → 不是就作废

2. 案例引用落地：
   模型说"参考了案例 A、B" → 系统核对"A、B 是否在检索结果里" → 不是就作废
```

为什么用**精确子串匹配**而不是"模型 + 置信度"：
- 语义相似会放过"拼接型幻觉"（把原文片段拆开再拼）；
- 用模型 B 核验模型 A 的输出 = 循环论证；
- 精确匹配是确定性的，**不会误放行**（被改写过的"引用"会被拒，这是故意的）。

## 第 3 步：存储层（35 张表 + Alembic）

### 目的

让数据**落库**：一次导入、一次分析、一条归因，都要能持久化、能查询、能追溯。

### 思路

```text
SQLAlchemy 模型（models.py）  ← 唯一真相
        │  alembic revision --autogenerate
        ▼
Alembic 迁移文件（versions/xxx_initial.py）
        │  alembic upgrade head
        ▼
PostgreSQL 34 张表
```

为什么用 PostgreSQL 而不是 SQLite：

| SQLite 的限制 | 影响 |
| --- | --- |
| 单写（同一时刻只能一个写事务） | 多 worker 并发写会互相锁 |
| 没有行级安全（RLS） | 前端阶段的租户隔离要靠它 |
| 没有 pgvector | Case RAG 的向量检索要用 |
| JSONB 性能弱 | 我们的 stats/attrs 大量用 JSON |

为什么用 Alembic 而不是 `create_all()`：
- `create_all()` 只建表、不记版本，改表只能 drop 重建（**数据丢**）；
- Alembic 记录每次变更，改表加一个 migration 即可，**不丢数据**。

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 数据没法持久化 | 34 张表覆盖全链路（导入→分析→执行→复盘） |
| 改表会丢数据 | Alembic 版本化迁移 |
| 表结构分散 | `models.py` 是唯一真相，按业务域分组 |
| 换数据库要改代码 | 连接串在 `.env`，代码不写死 |

### 数据流

```text
.env（HUB_STORAGE__URL=postgresql+psycopg://...）
   │  Settings 读取
   ▼
db.py（engine + SessionLocal）
   │  repository.py 封装读写
   ▼
业务代码（不写 SQL、不碰 Session）
```

### 34 张表的分组

| 组 | 表 | 服务于 |
| --- | --- | --- |
| 数据接入与质量 | `ingest_batch` / `record` / `review_feature` / `sku_mapping` / `price_snapshot` | 03/04/05 |
| 运行与分析 | `analysis_run` / `issue_cluster` / `anomaly` | 06/07 |
| 执行 | `action_proposal` / `tool_execution` / `idempotency_record` / `hitl_task` / `dead_letter` | 08/09 |
| 可观测与评估 | `trace_span` / `judge_score` / `model_registry` / `eval_case` / `eval_result` | 10 |
| 业务数据面 | `spu_catalog` / `sales_daily` / `incremental_cursor` / `platform_field_map` / `promo_calendar` | 07 |
| 效果复盘 | `action_outcome` | 09 |
| 回复与申诉 | `review_reply_draft` / `review_appeal` | 11 |
| 协同与报表 | `notification` / `report_job` / `report_field_whitelist` | 11 |
| 账号/租户/审计/知识 | `tenant` / `app_user` / `audit_log` / `knowledge_entry` | 前端阶段 |
| 案例库 | `case_entry` | 07（M4 Case RAG） |

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `sqlalchemy.orm.DeclarativeBase` + `Mapped` + `mapped_column` | SQLAlchemy 2.0 声明式建表 |
| `sqlalchemy.dialects.postgresql.UUID / JSONB / ARRAY / INET` | PG 专用类型 |
| `alembic revision --autogenerate` | 从模型自动生成迁移 |
| `alembic upgrade head` | 执行迁移建表 |
| `psycopg` | PG 驱动 |

### 踩的坑（这一步坑最多）

#### 坑 1：`UUID` 名字冲突

```python
# ❌ 这样写：UUID 被 SQLAlchemy 的类型覆盖了
from sqlalchemy.dialects.postgresql import UUID
id: Mapped[UUID] = mapped_column(UUID(as_uuid=True))   # Mapped[UUID] 里的 UUID 是错的

# ✅ 正确：Python 类型和 SQLAlchemy 类型分开命名
from uuid import UUID
from sqlalchemy.dialects.postgresql import UUID as PGUUID
id: Mapped[UUID] = mapped_column(PGUUID(as_uuid=True))
```

#### 坑 2：写完全量表后，旧的 repository 还在引用旧类

34 张表重写后，`models.py` 里的 `Run` 变成了 `AnalysisRun`，但 `repository.py` 还在 `from hub.persistence.models import Run`——**一跑就 ImportError**。

**教训**：大规模重构后，要全文搜索被改名/删除的符号。

#### 坑 3：`alembic.ini` 里的中文导致 GBK 解码错误

**现象**：
```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x93 ...
```

**原因**：Alembic 用**系统编码**（中文 Windows 是 GBK）读 `alembic.ini`，而文件里写了中文注释（UTF-8）。

**解决**：`alembic.ini` 里**只写英文**。

**教训**：
- `.ini` 配置文件不要写非 ASCII 字符；
- `.py` 文件写中文没事（Python 3 默认 UTF-8）。

#### 坑 4：`.env` 用相对路径，换个目录就找不到

**现象**：配置读到的是 `sqlite:///hub.db`，不是 PG。

**原因**：`env_file=".env"` 是相对当前工作目录的，从别的目录跑就找不到。

**解决**：用绝对路径：

```python
_ENV_FILE = Path(__file__).resolve().parents[2] / ".env"
model_config = SettingsConfigDict(env_file=str(_ENV_FILE), ...)
```

#### 坑 5：终端跑脚本找不到 `hub` 包

**现象**：`ModuleNotFoundError: No module named 'hub'`。

**原因**：`python tests/xxx.py` 时，Python 只把 **`tests/`** 加进 `sys.path`，没有 `backend/`。（PyCharm 会自动加，所以 IDE 里能跑、终端里不能跑。）

**解决**：在每个测试脚本开头手动加：

```python
_BACKEND_DIR = Path(__file__).resolve().parents[1]
if str(_BACKEND_DIR) not in sys.path:
    sys.path.insert(0, str(_BACKEND_DIR))
```

#### 坑 6：测试脚本固定哈希，第二次跑撞唯一约束

**现象**：`UniqueViolation: 重复键违反唯一约束 "uq_batch_hash"`。

**原因**：测试脚本用固定 `file_sha256="0"*64`，第二次跑就重复了。

**结论**：**唯一约束在正常工作**（防止同一个文件重复导入）。修测试脚本，每次用唯一哈希。

**教训**：测试数据必须"每次唯一"，否则第二次跑就失败。

## 第 4 步：walking skeleton（8 步桩）

### 目的

**先验证"管子通不通"**，再往管子里灌水。

具体验证三件事：
1. 模块能按顺序拼装；
2. 数据能在步骤之间传递；
3. 每步能落库、能追踪。

### 思路

```text
ingest → dqe → multimodal → graph → analysis → gateway → execution → retro
（8 个桩函数，返回假数据，但签名与真实实现一致）
```

每个桩只返回一个假字典，比如：

```python
def stub_dqe(state):
    return {"kept": 30, "review": 3, "dropped": 3}
```

等真实模块写完，只要把 `stubs.py` 里的函数换成真函数，**runner 一行都不用改**。

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 等所有模块写完才能联调 | 先用桩跑通全链 |
| 出问题分不清是结构错还是逻辑错 | 结构先用桩验证，再填逻辑 |
| 失败不可观测 | 每步一个 span，失败标 ERROR |

### 数据流

```text
PipelineState(trace_id, batch_id, tenant_id, outputs={})
   │  每一步读取需要的输入、把产出写进 outputs
   ▼
outputs = {
    "ingest": {"records": 36},
    "dqe": {"kept": 30, ...},
    ...
}
```

同时每步写一条 `trace_span`（起止时间、状态、属性），最终 `analysis_run` 从 QUEUED → RUNNING → DONE。

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `contextlib.contextmanager` | 写 span 上下文管理器 |
| `argparse` | CLI 子命令 |
| `sqlalchemy.select` / `func.count` | 验证落库 |

### 踩的坑

无（一次通过）。

验收命令：

```powershell
python -m hub.cli skeleton
```

输出：8 步全部打印、`analysis_run.status=DONE`、`trace_span 共 8 条`。

## 第 5 步：数据接入适配器

### 目的

把商家导出的 **xlsx 文件**，变成归一化的 `Record`。

这一步是整个系统的"入口"——数据质量决定了后面所有分析的上限。

### 思路

**映射表驱动 + 分层处理：**

```text
xlsx
 │  reader.py    读全部行
 ▼
rows
 │  reader.py    探测表头（前 10 行找命中列名最多的）
 ▼
(表头行, 列映射)
 │  adapter.py   逐行：原始列名 → 统一字段名
 ▼
raw fields
 │  normalize.py 金额/评分/时间/整数 归一化
 │  pii.py       昵称丢弃、正文手机号脱敏
 ▼
Record 或 BadRow
```

关键设计：**坏行不中断**。一行解析失败记一条 `BadRow`，继续处理下一行，最后在 `MappingReport` 里告诉你有多少坏行、为什么坏。

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 两平台列名不同（订单编号 vs 评论ID） | 映射表 `MAPPINGS[(platform, data_type)]` |
| 表头不在第一行 | 扫描前 10 行，找命中已知列名最多的一行 |
| 中间有空行、末尾有合计行 | `is_empty_row` / `is_total_row` 跳过 |
| 金额带符号千分位（￥1,299.00） | `parse_money` 清洗后转 `Decimal` |
| 淘宝"好中差" vs 京东"1-5 星" | `parse_rating` 按平台归一成 1~5 |
| 昵称是 PII | 直接丢弃，只计数 |
| 正文含手机号/微信号 | `mask_text` 脱敏 |
| 坏数据让整批导入失败 | 坏行隔离，不中断 |

### 数据流（详细）

```text
jd_review_202610.xlsx
   │  openpyxl 读
   ▼
[2010 行]  ← 2000 正常 + 10 条连续刷评注入
   │  detect_header → 第 1 行是表头，命中 13 个列名
   ▼
逐行：
   "评论ID"     → platform_review_id
   "商品编号"   → platform_spu_id
   "评价星级"   → rating（parse_rating → 5）
   "评价内容"   → content（mask_text 脱敏）
   "评价时间"   → review_time（parse_datetime）
   "商品单价"   → price（parse_money → Decimal）
   "用户昵称"   → nickname（PII，丢弃）
   ▼
Record(
    platform="jd",
    rating=5,
    fields={"content": "...", "title": "...", ...},
    monetary={"price": Decimal("99.00")},
    ts=2026-09-16 22:33:54,
    impl="ingress.v1"
)
```

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `openpyxl.load_workbook(read_only=True, data_only=True)` | 读 xlsx（只读、只取值） |
| `ws.iter_rows(values_only=True)` | 逐行读 |
| `decimal.Decimal` | 金额防精度丢失 |
| `datetime.strptime` | 多格式时间解析 |
| `re` | 金额清洗、手机号/微信号识别 |
| `hashlib.sha256` | 文件指纹（幂等） |

### 踩的坑

#### 坑 1：`rating` 算了但没放进结果

**现象**：用户发现输出里没有 `rating`。

**原因**：`_build_review` 里算了 `rating` 用来校验，但**忘了**放进结果。

**教训**：算了的值要检查有没有"用出去"。

#### 坑 2：`rating` 放错位置（应在 Record 顶层）

**现象**：用户指出"`rating` 是核心必填字段，应该在顶层，不该塞进 `fields` 通用字典"。

**原因**：`fields` 是"通用键值对"，而 `rating` 是**每类评价都有的核心字段**，而且数据库 `record` 表里本来就是独立列。

**修复**：
```python
class Record(BaseModel):
    ...
    rating: int | None = None   # ← 顶层字段
    fields: dict = {}           # 通用字段（content/title/attr...）
```

**教训**：核心、必填、要参与查询/统计的字段，放顶层；只有"平台特有、可有可无"的才放 `fields`。

#### 坑 3：mock 数据把 Python 列表写进了评论

**现象**：评价内容是 `['黑色', '卡其', '灰色']的休闲裤男直筒...`。

**原因**：`generate_mock.py` 里 `attrs.get("颜色")` 拿到的是列表，直接 `f"{color}"` 把列表的 repr 写进去了。

**修复**：
```python
# ❌ f"{colors}" → "['黑色', '卡其', '灰色']"
# ✅ 随机取一个
color = random.choice(colors) if isinstance(colors, list) else colors
```

**教训**：生成测试数据时，`str(列表)` 是个高频坑——要养成"取单个值"的习惯。

## 第 6 步：导入落库

### 目的

把适配器产出的 `Record`（内存对象）**写进数据库**。

为什么必须落库，而不是"内存传给下一步"：

- 数据要**可追溯**（"这次分析用的是哪批数据"）；
- 要能**重跑**（不用重新读 2000 行文件）；
- DQE、归因、分析都从库里按 `batch_id` 查，天然解耦。

### 思路

**三种数据类型分三张表**（表结构不同，不能硬塞一张）：

| 数据类型 | 目标表 | 原因 |
| --- | --- | --- |
| review | `record` | 有 rating / content / review_time |
| product | `spu_catalog` | 有 category / price / stock |
| sales | `sales_daily` | 有 stat_date / gmv / uv（日粒度聚合） |

**幂等三层**：

| 层级 | 规则 | 实现 |
| --- | --- | --- |
| 文件 | 同一文件（tenant+platform+sha256）只导一次 | 先查 `ingest_batch`，存在就跳过 |
| 记录 | 同一条评价（platform+platform_review_id）跳过 | `ON CONFLICT DO NOTHING` |
| 商品/销售 | 有则更新 | `ON CONFLICT DO UPDATE` |

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 数据只在内存、不能追溯 | 落 `record` / `spu_catalog` / `sales_daily` |
| 重复导入产生重复数据 | 三层幂等 |
| 导入时还没跑 DQE，但表要求非空 | `dqe_*` 三列改为可空，DQE 回填 |
| 大批量插入慢 | `pg_insert` 批量插入（一条 SQL 写 1991 行） |

### 数据流

```text
list[Record]（适配器产出）
   │  IngressRepo.save()
   ▼
1. 查 ingest_batch：同文件已导？ → 是：直接返回已有批次
2. 写 ingest_batch（状态 DONE）
3. 按 data_type 分派：
     review  → record        （ON CONFLICT 跳过）
     product → spu_catalog   （upsert）
     sales   → sales_daily   （upsert）
   ▼
数据库（可查、可重跑）
```

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `sqlalchemy.dialects.postgresql.insert` | PG 批量插入 |
| `.on_conflict_do_nothing(index_elements=...)` | 记录级跳过（幂等） |
| `.on_conflict_do_update(index_elements=..., set_=...)` | 商品/销售 upsert |
| `hashlib.sha256` | 正文指纹（`content_sha256`，R007 去重用） |

### 踩的坑

#### 坑 1：`record` 表的 DQE 字段是 `NOT NULL`，导入时填不了

**现象**：设计文档的 `review` 表里 `dqe_decision / dqe_reason_code / dqe_engine` 是 `NOT NULL`，但导入时还没跑 DQE。

**原因**：设计文档假设"导入即降噪"（DQE 在导入时同步跑），而我们的架构把导入和 DQE 拆成了两步。

**修复**：把这三列改成**可空**（`NULL` = 尚未判定），新增一个 Alembic 迁移。

**教训**：设计文档的 DDL 是按"理想流程"写的，实现时如果流程被拆分，要敢于改 schema，而不是用假值糊弄（比如写 `dqe_decision='keep'` 就是撒谎）。

#### 坑 2：`Record` 契约是通用的，表是固定的

**现象**：`Record` 用 `fields` dict 装业务字段，但 `record` 表是固定列（`content_clean` / `rating` / `has_image`...）。

**解决**：写一层显式转换 `_to_record_row`，把 dict 映射到列。

**教训**：契约（通用）和存储（固定）本来就不该是同一套结构，中间必须有转换层——这层就是"防腐层"，避免表结构污染契约。

### 验收

```powershell
python tests/check_import.py
```

验收标准：

- 首次导入：`record` 表写入 1991 条；
- 重复导入：`被跳过=True`，不产生重复；
- `dqe_decision` 为 `NULL`（待 DQE 回填）；
- `content_sha256` 有值。

## 第 7 步：M1 DQE 数据降噪

### 目的

把导入的评价判定为 `keep / review / drop`，挡住**水军、灌水、广告、Prompt 注入、复制粘贴刷屏**。

数据质量决定分析上限——如果 40% 的水军进了分析，后面的聚类、归因全是噪音。

### 思路

**两条轨 + 一个融合**：

```text
record 表（dqe_decision IS NULL）
   │ 按 batch_id 分组（R007 需要同批次比较）
   ▼
① 归一化（NFKC / 去零宽 / 剥 HTML / 压缩重复）
   ▼
② 规则轨（9 条硬规则，纯 Python，模型挂了也能跑）
   │  R001 太短 / R002 非中文 / R003 纯符号 / R004 联系方式
   │  R005 广告 / R006 模板 / R007 近似重复 / R008 注入
   ▼
③ ML 轨（TF-IDF + 逻辑回归 → spam_score 0~1）
   ▼
④ 决策融合（规则优先 + 差评保护）
   ▼
⑤ 回填 record 表的 dqe_* 字段
```

**为什么规则轨是兜底**：模型文件可能被删、版本不匹配、依赖缺失，但纯 Python 规则永远可用。降级时 `engine="rule_only"`，主链继续。

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 水军/灌水/广告 | 规则轨 R001–R006 |
| 复制粘贴刷屏 | R007 近似重复（Jaccard ≥ 0.6）+ **时间窗 24h** |
| Prompt 注入 | R008 关键词 + **唯一硬 drop**（差评也不降级） |
| 误杀真实差评 | R009 差评保护：`rating ≤ 2` 的 drop 降级为 review |
| 规则写不完的细微水军 | ML 轨（TF-IDF + 逻辑回归） |
| 模型挂了怎么办 | 自动降级 `rule_only`，不中断主链 |
| 障眼法绕过 | 归一化（零宽字符、全角、HTML、重复字符） |

### 数据流（四层）

```text
1. 文本层：content_clean → normalize() → 干净文本
2. 特征层：TF-IDF(字符 2-4) + TF-IDF(jieba 词) → 稀疏向量（实测 2224 维）
3. 判定层：规则命中列表 + spam_score → decide() → DQEVerdict
4. 存储层：executemany 批量回填 record 表的 6 个字段
```

### 调用的关键 API

| API | 用途 |
| --- | --- |
| `sklearn.TfidfVectorizer` | 文本 → TF-IDF 稀疏向量 |
| `sklearn.LogisticRegression` | 分类器（输出概率） |
| `scipy.sparse.hstack` | 拼接字符特征 + 词特征 |
| `jieba.lcut` | 中文分词 |
| `joblib.dump/load` | 模型持久化 |
| SQLAlchemy executemany | 批量回填（一次 SQL 更新 3973 行） |
| `unicodedata` | NFKC 归一化、字符分类 |

### 关键设计决策

| 决策 | 为什么 |
| --- | --- |
| **Jaccard 替代 simhash** | simhash 对短文本不稳定（实测相似文本距离 8~14，远超阈值 3） |
| **R007 加时间窗** | 刷屏是"集中爆发"，正常相似评价是"散布在几个月"；不加时间窗误杀 80% |
| **差评阈值更高（0.90 vs 0.75）** | 差评更难被 ML 判死，宁可放过不可误杀 |
| **R008 不可降级** | 注入是攻击，差评也硬 drop，否则攻击能穿透差评通道 |
| **规则按"具体度"排序** | `hits[0]` 写进 reason_code，要报最具体的（R006 模板 > R001 太短） |
| **ML 输出概率而非 0/1** | 阈值可调，不用重训模型 |

### 踩的坑（这一步坑最多）

#### 坑 1：simhash 对短文本失效

**现象**：相似文本（改一个字）汉明距离 10~14，远超阈值 3，抓不到近似重复。

**原因**：simhash 靠"逐 token 投票"，短文本 token 少（8~15 个），票数边际小，一改就翻多位。

**解决**：改用字符 bigram 的 Jaccard 相似度（阈值 0.6）。simhash 代码保留（长文本仍适用、有教学价值），但不作为 R007 主判据。

#### 坑 2：`jieba.lcut` 不能被 pickle

**现象**：`joblib.dump` 报 `cannot pickle '_thread.RLock' object`。

**原因**：`jieba.lcut` 是 Tokenizer 单例的绑定方法，持有 `threading.RLock`。

**解决**：包一层模块级函数 `jieba_tokenize`（`hub/dqe/ml.py`），pickle 只记函数引用。

#### 坑 3：SQLAlchemy 批量更新两个坑

**现象 1**：`bulk synchronize of persistent objects not supported...`
**现象 2**：`No primary key value supplied for column(s) record.id`

**原因**：`update(ORM类)` 会触发 ORM 的"批量更新"机制，它要么要同步会话对象，要么以为是"按主键批量更新"。

**解决**：改用 Core 写法——`s.connection().execute(update(表对象).where(...), params)`。批量更新别走 ORM 的 `execute`。

#### 坑 4：R007 误杀 87%（**最有价值的一个**）

**现象**：降噪率 87%，远高于 mock 数据的 40% 噪音比例。reason 分布显示 R007 抓了 3177 条。

**原因**：mock 的正常评价是"模板句"（只有 7 个正面模板），几千条里大量重复，Jaccard 一算全判重。

**解决**（两步）：
1. **加时间窗 24h**：刷屏是集中爆发，正常相似评价散布在 90 天里。降噪率 87% → 63.5%。
2. **治本：修 mock 数据**：模板池 7→25 个、`fill()` 总是带商品标题、加 30 个随机细节。降噪率 63.5% → 43.6%。

**教训**：**算法要和数据匹配**。simhash 适合长文本、Jaccard 适合短文本、"重复"要结合时间维度——脱离数据特性谈算法都是空谈。

#### 坑 5：mock 数据模板化导致指标虚高

**现象**：训练集 F1 = 1.000（满分）。

**原因**：mock 的水军太"标准"（模板、重复、纯英文），TF-IDF 直接记住模板词。

**结论**：1.0 不是模型好，是**夹具太简单**。真实数据预计 0.8~0.9。

#### 坑 6：`fill()` 把列表 repr 写进评论

**现象**：评价内容是 `['黑色', '卡其', '灰色']的休闲裤…`。

**原因**：`attrs["颜色"]` 是列表，直接 `f"{color}"` 会写出列表的 repr。

**解决**：`random.choice(colors)` 取单个值。

### 验收

```powershell
python tests/check_engine.py     # 分布 + 差评保护
python tests/check_accuracy.py   # 用 gold_labels 算准确率
```

**实测结果**（3973 条）：

| 指标 | 结果 |
| --- | --- |
| keep / drop | 2241 / 1732 |
| 降噪率 | **43.6%**（mock 噪音 40%，吻合） |

### 遗留与债务（本步新增）

| 类型 | 内容 |
| --- | --- |
| 遗留 | 异常检测（孤立森林）未做——设计文档要的 8 维特征有 3 维拿不到（下单时延、用户历史评价数、情感极性） |

## 第 8 步：M2 多模态沙箱（阅后即焚 + 元数据剥离）

### 目的

让系统"看懂"买家秀图片（破洞、污渍、色差），**同时保证图片阅后即焚**——图片是用户隐私，不能留、不能外传。

这一步的价值不在"调 Vision 模型"，而在**合规的图片生命周期管理**。

### 前置讨论：图片来源怎么选（差点踩坑）

最初想做"按图片 URL 下载"，研究后发现三条路：

| 方式 | 合规性 | 门槛 |
| --- | --- | --- |
| 平台开放 API | ✅ 合规 | 高（ISV 资质 + 商家授权） |
| **商家上传图片包** | ✅ **零风险** | 低 |
| 爬虫抓 URL | ❌ 违反平台协议 + 隐私 | 低但不能做 |

**最终选"商家上传"**——和已有的"评价 Excel 手动导入"完全一致，系统不碰任何平台，零法律风险。

### 思路

```text
商家上传的图片包（目录 / zip）
   │
   ▼
① 沙箱（优先 /dev/shm 内存盘，Windows 退化为临时目录）
   │
   ▼
①.5 **元数据剥离**（像素级重建：GPS/设备信息物理上不存在）
   │
   ▼
② pHash 去重（同一张图只调一次模型）
   │
   ▼
③ Vision 打标（本地 Qwen2.5-VL-3B，图片不出本机）
   │
   ▼
④ 跨模态融合（图片发现 + 文字定性）
   │
   ▼
⑤ 覆写销毁（随机字节覆盖 + fsync + unlink）
   │
   ▼
review_feature（只留标签 + 哈希，不留原图）
```

### 解决了什么问题

| 问题 | 怎么解决 |
| --- | --- |
| 图片隐私 | tmpfs + 覆写销毁，原图不留痕 |
| **图片里的 GPS/设备信息** | **元数据剥离**（像素级重建，白名单） |
| 同一张图重复调模型 | pHash 去重（16×16，256 位） |
| 图片不出本机 | 本地 Ollama + Qwen2.5-VL-3B |
| 模型分不清"污渍还是破损" | 文字补类别（跨模态） |
| Vision 挂了 | 单张失败降级，不中断整批 |
| 法律风险 | 商家上传，不爬取 |

### 数据流（详细）

```text
record 表（has_image=true，且还没 review_feature）
   │ 取 image_urls（一条评价 1~9 张）
   ▼
图片包（data/mock/images/）
   │ 逐张按 URL 的 basename 找文件
   ▼
沙箱（tmpfs）
   │ 逐张计算 pHash
   ▼
pHash 已见过？ ──是──→ 复用标签（不调模型）
   │否
   ▼
Ollama /api/chat（Qwen2.5-VL-3B）
   │ 每张返回 JSON → VisionTags
   ▼
多图聚合：取最严重的一张
   │
   ▼
defect_type == "其他"？ ──是──→ 用评价文字补类别
   │
   ▼
写 review_feature（一条评价 1 条，不是 1 图 1 条）
   │
   ▼
退出沙箱 → 覆写销毁所有图片
```

### 多图聚合规则（一条评价 1~9 张）

`review_feature` 是 **1:1**（一条评价一条记录），所以多图必须聚合：

| 字段 | 聚合方式 | 为什么 |
| --- | --- | --- |
| `defect_type` | 取 severity 最高的那张 | 最严重的问题才是这条评价的核心 |
| `severity` | 取最大 | 一张严重就算整体严重 |
| `color_deviation` | 取最大 | 某张色差明显就算明显 |
| `ocr_text` | 取第一个非空的 | OCR 文本通常只有一张有 |
| `confidence` | 取最严重那张的 | — |

**实测**：89 条评价 × 165 张图 → **89 条 `review_feature`**，检出 17 个缺陷
（单图时只检出 12 个——多一张图就多一次"发现"的机会）。

### 调用的关键 API

| API | 用途 |
| --- | --- |
| Ollama `POST /api/chat` | 本地视觉模型推理（`images` 字段传 base64） |
| `urllib.request` | 标准库发 HTTP，零额外依赖 |
| `PIL.Image` | 读图、转灰度、pHash |
| `os.urandom` + `fsync` + `unlink` | 覆写销毁 |
| `tempfile.mkdtemp` / `/dev/shm` | 沙箱目录 |

### 踩的坑（这一步坑最多，共 8 个）

#### 坑 1：提示词里的 JSON 示例被照抄

**现象**：10 张瑕疵图全输出 `none`，连有破洞的图也是。

**原因**：提示词里给了带具体值的示例
`{"defect_type": "none", "severity": 0, ...}`，3B 模型**原样照抄**。

**验证**：同一个模型，问"这张图里是什么"它能准确描述
（"灰色的裤子，裤子上有一个破洞"）——说明它**看见了**，只是输出时抄了示例。

**解决**：
1. 示例改成**占位符** `<none或破损或...>`；
2. 加"先描述、再判断"（CoT）。

**结果**：瑕疵图从 `none` 变成 `破损`，正常图仍然 `none`。

#### 坑 2："其他"成了模型的"避难所"

**现象**：正常图被判成 `其他` 而不是 `none`。

**原因**：选项里有"其他"，模型不确定时就选它——**看起来输出了有效答案，实际是逃避判断**。

**解决**：明确"没问题必须填 none""有具体问题优先选具体类别"。

#### 坑 3：改成"对号入座"反而更差

**现象**：把类别定义写成"衣服上有洞 → 破损"这种具体描述后，检出率从 9/10 掉到 **5/10**。

**原因**：模型把"对号入座"理解成"对不上就 none"，变得极其保守。

**解决**：回退到"类别列表 + 简短定义"那版。

**教训**：**3B 模型对提示词极度敏感**，一句话的措辞就能让结果天差地别。不要以为"说得越清楚越好"。

#### 坑 4：两阶段（先二分类再细分类）反而更差

**假设**：拆成"有没有问题"+"属于哪类"两步，应该更准。

**实测**：

| 方式 | 检出 |
| --- | --- |
| 单阶段 | **9/10** |
| 两阶段·二分类 | **6/10** |

**原因**：单阶段的提示词里**给了类别定义**（"色差 = 图片里出现不自然的颜色块"），
等于告诉模型"该找什么"；二分类问题太干，模型容易说"没有"。

**教训**：**不是步骤拆得越细越好，而是给模型的上下文越充分越好。**

#### 坑 5：pHash 8×8 太粗，误判 13/50

**现象**：50 张不同图片，只算出 37 个不同哈希——13 张被误判成"同一张"。

**风险**：如果瑕疵图和正常图撞了哈希，瑕疵图会复用正常图的 `none` 标签 → **漏检**。

**解决**：pHash 从 8×8（64 位）升到 **16×16（256 位）**。
改完 93 个文件 → 50 次 Vision 调用，**正好等于 50 张真实图**。

#### 坑 6：mock 的图片和文字是随机配对的

**现象**：加了"文字补类别"后，4 条"其他"一条都没补上。

**原因**：这 4 条评价的文字是"缩水了""面料扎人""实物很薄"——
**和图片里显示的缺陷不是一回事**。因为 mock 生成时，
图片是随机分配的，文字是随机模板抽的，两者无关。

**真实场景**：顾客拍图就是为了说明他抱怨的问题，图文是相关的。

**结论**：融合逻辑**是对的**（单元测试通过、定向测试验证过），
只是 mock 数据体现不出来。等接真实数据自然生效。

#### 坑 7：统计口径混了（评价数 vs 图片数）

**现象**：多图上线后，报告显示"待处理 89 条 / 去重 115"——**去重比处理还多**。

**原因**：`processed` 数的是**评价**，`deduped` 数的是**图片**。
单图时 1:1 看不出来，多图后（89 条评价 / 177 张图）就露馅了。

**解决**：报告拆成两行，单位写清楚：
```text
评价：待处理 89 条，成功 89
图片：共 177 张｜pHash 去重 115 张｜实际调 Vision 62 次
```

**教训**：**统计指标一定要标单位**。单图时代埋的雷，多图时代才爆。

#### 坑 8（后期补的）：只做了"阅后即焚"，漏了"图片里有什么"

**这是本项目最值得记的一个坑。**

**现象**：M2 上线后，设计文档的"P0 简化清单"里一直挂着一条 🔴：

```text
| 1 | 图片 ≤5MB、格式校验、剥 EXIF（含 GPS） | 未做 | 🔴 隐私 |
```

**根因**：我们把"隐私"理解成了**"不留副本"**，于是做了 tmpfs + 覆写销毁。但真正的隐私风险是**"副本里有什么"**——买家 iPhone 拍的照片，EXIF 里带着 GPS 坐标（精确到米）、设备型号、拍摄时间。

```text
阅后即焚  = 不留副本
元数据剥离 = 副本里不留隐私
只做前者，等于"把带 GPS 的照片烧掉了" —— 烧掉之前它已经在系统里了
```

**为什么一直没被发现**：
mock 图片是通义万相生成的，**本来就没有 EXIF**。风险在我们的数据上完全不可见——这和"mock 图文随机配对导致跨模态融合测不出来"是同一类问题：**测试数据太干净，掩盖了真实风险**。

**解决：像素级重建，而不是删 EXIF 标签**

```python
clean = Image.frombytes("RGB", size, pixels)   # 全新对象，.info 为空
```

| 做法 | 性质 | 问题 |
| --- | --- | --- |
| `img.info.pop("exif")` | 黑名单 | JPEG 在 APP1、PNG 在 tEXt、WebP 在 EXIF chunk；内嵌缩略图可能单独带 GPS |
| **`Image.frombytes` 重建** | **白名单** | 只保留像素，**元数据物理上不存在** |

**落点**：`Sandbox.ingest()` 里、拍平之后、返回之前——**任何下游处理（pHash / Vision / 日志）之前**。

**验证**（`tests/check_exif.py`）：

```text
原始：884 字节，GPS(39.9042N, 116.4074E) + 设备型号
剥离后：694 字节，EXIF/GPS 全无，尺寸仍 64×64
实测 177/177 张全部剥离成功
```

**教训**：
1. **"不留副本"和"副本干净"是两件事**，隐私方案必须同时覆盖；
2. **allow-list 永远比 deny-list 可靠**——"只保留需要的"比"删掉已知有害的"安全；
3. **只用干净数据测试隐私功能 = 没测试**。要造"带 GPS 的图"来验证。

### 关键设计决策

| 决策 | 为什么 |
| --- | --- |
| 图片来源 = 商家上传 | 零法律风险（不爬平台） |
| 图片阅后即焚 | 隐私合规（随机字节覆写 + fsync + unlink） |
| **元数据剥离（像素重建）** | **"不留副本"之外还要"副本干净"**——GPS/设备信息物理上不存在 |
| **M2 写 `analysis_run`（审计）** | 控制台输出不留存、不可审计；写库才能证明"剥离 + 销毁"真发生了 |
| pHash 16×16 | 8×8 太粗，实测 13/50 误判 |
| 单阶段分类 | 实测比两阶段好（9/10 vs 6/10） |
| 提示词用占位符 | 带具体值的示例会被小模型照抄 |
| 跨模态融合 | 图片擅长"发现"，文字擅长"定性" |
| Vision 可插拔 | Mock（测试）/ Ollama（本地）/ 云端（未来） |
| 多图聚合（取最严重） | 一条评价多张图时，最严重的问题才是核心 |

## 第 9 步：M3 归因链（分类 + 归因）

### 目的

把 **366 条差评**变成"什么问题、多严重、证据在哪、集中在哪个品类"。

两条产出：

| 产出 | 粒度 | 存哪 |
| --- | --- | --- |
| 每条差评的主题 | 366 条 | `review_topic`（新表） |
| 每类问题的归因 | 12 条（6 主题 × 2 平台） | `analysis_run.stats`（JSONB） |

### 前置讨论：先定死 35 件事

M3 是项目核心，**动手前把"怎么做"和"可能的问题"全讨论清楚**。关键决策：

| 决策 | 结论 | 为什么 |
| --- | --- | --- |
| 产出粒度 | 分类 + 归因都做 | 分类可用 gold 评测，归因有业务价值 |
| 链条 | 分类 → SQL 聚合 → 归因 | 聚合是数数，不该让 LLM 干 |
| 输入范围 | 差评（rating ≤ 2）+ DQE keep | 好评不需要归因 |
| 存储 | 新建 `review_topic` 表 | 和 `review_feature` 对称（一模块一表） |
| 归因粒度 | topic × 平台 | 跨平台差异才是"跨平台中枢"的价值 |
| 小格子 | < 5 条跳过 | 证据不足时归因只能瞎编 |
| 代表评价 | **按长度降序** | 归因要"信息量"，不是"情绪强度" |
| 置信度 | **规则算** | 3B 的 self-confidence 恒 1.0，不可信 |
| 降级 | 批量 → 逐条 → 关键词 | 三级 |
| 评测 | gold_labels 的 75 条 | 唯一合法的"人工标注" |

### 思路

```text
366 条差评
   │
   ├─① 分类（LLM，批量 10 条）──→ review_topic（366 条）
   │
   ├─② 聚合（SQL，零 LLM）─────→ 12 个格子（topic × 平台）
   │
   ├─③ 归因（LLM，每格 1 次）───→ Attribution（解释 + 证据）
   │
   └─④ 统计（SQL）────────────→ by_category / by_platform
```

**为什么这样切**：

| 环节 | 交给谁 | 理由 |
| --- | --- | --- |
| 分类 | LLM | 理解语义，3B 的舒适区（单条/批量都稳） |
| 聚合 | SQL | 数数而已，LLM 干这个又慢又不准 |
| 归因 | LLM | "看出一组差评的共同点"是语言任务 |
| 统计 | SQL | 品类/平台分布是确定性计算，绝不能估 |

### 数据流（详细）

```text
record（rating ≤ 2 且 dqe_decision='keep'，且没有 review_topic）
   │
   ▼
① 批量分类（每批 10 条，编号 R1..Rn）
   │  → 校验：id 在输入里、topic 在枚举里、数值截断
   │  → 失败降级：逐条重试 → 关键词兜底
   ▼
review_topic（record_id / topic / severity / confidence / impl / degraded）
   │
   ▼
② 聚合：SELECT topic, platform, count(*) GROUP BY
   │
   ▼
③ 每格取代表评价（长度降序、severity 次之，最多 10 条）
   │
   ▼
归因（LLM）→ explanation + evidence[]
   │  → quote 三级匹配 + 反查编号
   │  → Attribution 契约校验（ground_evidence）
   ▼
analysis_run.stats（attributions + cells + by_topic + by_platform）
```

### 两个核心提示词

**分类**（批量 10 条）：

```text
你是电商评价分类助手。下面有 10 条差评，每条以 [R1] 到 [R10] 开头。
请为每条判断它属于哪个问题：quality / size / logistics / service / desc_mismatch / misship / other
如果一条评价同时提到多个问题，选最强烈、最具体的那个。
如果评价里有夸有贬，以负面表述为准。
输出 JSON 数组，条数必须等于 10：[{"id": "R1", "topic": "quality", "severity": 3, "confidence": 0.9}]
```

**归因**（每格 10 条）：

```text
这些差评里最主要的 1 到 2 个问题是什么？（具体到"缝线""面料""掉色"；
不要罗列每一条评价的症状；不要引用 R 编号）
挑 1 到 5 条最能代表问题的原文，逐字原样引用（每条 4 到 80 字）
输出 JSON：{"explanation": "...", "evidence": [{"id": "R1", "quote": "逐字引用"}]}
```

### 踩的坑（8 个，都是真问题）

#### 坑 1：契约内部矛盾——`quote` 的 `min_length=4` 干掉了图片证据

```python
quote: str = Field(min_length=4)   # 为"文本摘录"设计的
```

但图片证据的 quote 是缺陷类型——`"破损"` 只有 **2 个字**，直接被字段校验拦下。

**解决**：字段放宽到 `min_length=1`，把"文本至少 4 字"挪到 `model_validator` 里按 signal 判断。

**教训**：**Pydantic 的字段约束是全局的**，不能依赖兄弟字段（`signal`）。

#### 坑 2：批量输出的 JSON 被 markdown 围栏包住 + max_tokens 不够

模型输出以 ```json 开头，或者被 `max_tokens` 截断 → `json.loads` 失败。

**解决**：先剥围栏再解析；`max_tokens` 从 600 提到 1000；失败时打印**完整原始输出**（不是前 80 字）。

#### 坑 3：模型给引用**补了个句号**

```text
模型：'...和描述一致。'    ← 末尾有句号
原文：'...和描述一致'      ← 没有
```

精确子串匹配 **100% 失败**，三个格子全军覆没。

**解决**：三级匹配——① 精确 → ② 去掉尾部标点 → ③ 规范化（只留中文/字母/数字）后定位，再映射回原文。

#### 坑 4：模型把 R6 的话安到 R5 头上

模型抄的**原文是真的**，但编号错了。

**解决**：**不盲信模型给的 ID**——先在声明的 ID 里找，找不到就在**所有原文**里反查。

#### 坑 5：解释里引用 R 编号，但归类是错的

```text
"缝线问题在 R1、R4、R7、R10 中提到"  ← R4 是"缩水"，不是缝线
```

**这比不写更伤信任**——运营去核对 R4 会发现对不上。

**解决**：提示词禁止引用 R 编号；定性交给模型，**精确出处交给 evidence 列表**（已 grounded），数量交给 SQL。

#### 坑 6：3B 是复读机，而且两句只差一个空格

```text
第2句：...效果不佳 ，如连衣裙...    ← "不佳" 后有空格
第3句：...效果不佳，如连衣裙...      ← 没有
```

精确去重失效。

**解决**：比较前**去掉序号和所有空白**再判重。

#### 坑 7：Alembic 重复跑 `revision` 生成空迁移

改完模型 → `revision`（有内容）→ `upgrade` → **再跑一次 `revision`**（因为没差异，生成空迁移）。

**解决**：空迁移无害但要删（`downgrade -1` + 删文件）。**正确顺序永远是：改模型 → revision → upgrade → 验证。**

#### 坑 8：字段名和契约不一致

`attribute_cell` 返回 `{"topic": ...}`，但契约字段叫 `root_cause` → 查看脚本 `KeyError`。

**解决**：内部返回值**对齐契约的字段名**，别图省事改名。

### 关键设计决策

| 决策 | 为什么 |
| --- | --- |
| `review_topic` 独立成表 | 生产者不同（M2/M3）、基数不同（89/366）、生命周期不同 |
| 聚合用 SQL 不用 LLM | 数数是确定性的，LLM 会算错还慢 |
| 归因按 topic × 平台 | 跨平台差异才是价值 |
| 小格子跳过 | 证据不足时归因只会瞎编 |
| 代表评价按长度 | 长评价信息量大，适合当证据 |
| confidence 规则算 | `min(0.95, 0.5 + 0.1 × 证据数)`，可解释 |
| 证据三级匹配 | 模型的引用"大意对、细节错"（句号/编号），要容错 |
| 不信模型给的 ID | 它抄的原文是真的，编号可能是错的 |
| 三级降级 | 批量 → 逐条 → 关键词，保证"每条都有结果" |
| 增量默认 | 日常只分类新增，`--force` 全量 |

- mock 差评是模板生成的，文本规整，**94.5% 是虚高的**；真实电商评论预计 70~80%；
- `service` 类最弱（F1 0.77）——"退运费/退款"这类问题容易被判成 misship；
- 解释文字偶尔有语义偏差（"发错尺码"被说成"尺码不符"），但**证据是准确的**。

## 关键设计决策汇总（为什么这么做）

| 决策 | 为什么 |
| --- | --- |
| 契约先行 | 避免"写到一半发现字段不对"，契约是唯一真相 |
| 精确子串校验证据 | 语义相似会放过"拼接幻觉"，精确匹配不会误放行 |
| 坏行隔离不中断 | 一批 2000 行里坏 20 行，不能因此整批失败 |
| 金额用 Decimal | float 精度丢失，钱必须精确 |
| PII 昵称直接丢弃 | 合规红线，只留计数不留值 |
| PostgreSQL + Alembic | 生产级、可迁移、支持 RLS/JSONB/pgvector |
| 先走路骨架 | 先验证管子通，再灌水，出问题好定位 |
| 8 步桩与真实实现同签名 | 换真实现时 runner 不用改 |
| 落库而非内存传递 | 可追溯（哪批数据）、可重跑、模块天然解耦 |
| 三种类型分三张表 | 评价/商品/销售结构差异太大，硬塞一张会全是 NULL |
| DQE 字段留空而非填假值 | 导入 ≠ 降噪，没判定就写 NULL，不撒谎 |
| 规则轨 + ML 轨双路 | 规则永远可用（兜底），ML 补规则写不完的细微特征 |
| Jaccard 而非 simhash 做判重 | simhash 对短文本不稳定（相似文本距离 8~14） |
| R007 加时间窗 | 刷屏是集中爆发，相似评价是分散的；不加窗口误杀 80% |
| 差评 drop 必须降级 review | 误杀真实差评的代价 > 多花 token |
| R008 唯一硬 drop | 注入是攻击，差评也不能放行 |
| 模型加载失败自动降级 | 主链不能因为模型文件被删就停摆 |
| 图片来源 = 商家上传 | 零法律风险（不爬平台、不违反协议） |
| 图片阅后即焚 | 隐私合规：不落盘、覆写销毁、只留标签 |
| 元数据剥离 | 像素级重建（白名单），EXIF/GPS 物理上不存在 |
| 提示词用占位符 | 小模型会照抄带具体值的 JSON 示例（实测 100% 照抄） |
| 单阶段 > 两阶段 | 实测 9/10 vs 6/10——定义是上下文，不是步骤 |
| pHash 16×16 | 8×8 太粗，50 张图误判 13 张 |
| 跨模态互补 | 图片擅长"发现"，文字擅长"定性" |
| 分类 + 归因分层 | 分类可评测（对 gold），归因有业务价值 |
| 聚合用 SQL | 数数是确定性的，LLM 会算错 |
| 归因按 topic × 平台 | 跨平台差异才是价值 |
| 证据三级匹配 | 模型引用"大意对、细节错"（句号/编号） |
| 不信模型给的 ID | 它抄的原文是真的，编号可能错 |
| confidence 规则算 | 3B 自评不可信，`0.5 + 0.1 × 证据数` |
| 小格子跳过 | 证据不足时归因只会瞎编 |
