## 二、生产形态定义（先定这个，别的都依附于它）

### 2.1 三条铁律

```text
① 图片永不出网（买家秀可能含人脸/门牌，剥 EXIF 不解决内容问题）
② 评价原文/客服内容永不出网（属于用户生成内容，平台条款通常禁止外发）
③ 只有【聚合统计】可上云（不可逆、不可识别到个人）
```

### 2.2 数据出网矩阵

| 数据 | 现在（mock 实验） | 生产 | 判断依据 |
| --- | --- | --- | --- |
| 聚合指标（差评率/簇条数/GMV） | ✅ 可上云 | ✅ 可上云 | 不可逆、不可识别 |
| `hub brief` 的输入（指标数字） | ✅ 可上云 | ✅ **可上云（唯一名正言顺的云端场景）** | 同上 |
| 评价原文（已脱昵称） | ✅ 可上云（数据是生成的） | ❌ **不出网** | 可识别（"我女儿穿 110 码"）+ 平台条款 |
| 买家秀图片 | ❌ 不上云（就算 mock 也不测） | ❌ 不出网 | 图像内容含 PII |
| 订单/客服对话 | — | ❌ 不出网 | 敏感个人信息 |

### 2.3 由此推导的"生产形态"

```text
M1 DQE / M2 多模态 / M3 归因 / M5 回复生成 / agent 规划
   → **本地模型**（7B）✅
hub brief
   → 云端或本地（只发数字）✅
前端 / API
   → 不出网（内网）✅
   ↓
**这就是"本地模型"这个卖点的真实含义**：
   不是"为了省钱"，是"用户数据不出网"
```

### 2.4 云端的两处正当用途

| 用途 | 说明 |
| --- | --- |
| **`hub brief`** | 只发聚合数字 → 可上云 ✅（而且云端的文字质量明显更好） |
| **实验/上限参考** | 在 mock 数据上测"若允许上云，规划能力能到多少" → **写进文档当边界说明**，不改变生产设计 ✅ |

> **如果将来客户允许上云**（法务 + 平台条款通过）：只改一个配置项，
> agent 即可从"受限形态"升到"完整形态" —— **这就是"客户端可切换"的真正价值**。

### 5.3 规划能力对照实验（0.5 天）

**两组，回答两个不同问题**：

| 组 | 测谁 | 回答 |
| --- | --- | --- |
| 同量级 | 7B 的不同家族（qwen2.5 / llama3.1 / glm-4-9b） | 是不是**这个模型**特别笨 → 若都差不多，**问题在提示词/任务分解** |
| 跨量级 | 7B vs 云端 | **规模**有没有用 |

**每组测三个数**：工具选择正确率（对照 `TOOL_BY_TOPIC`）｜3 步内完成率｜每步 token。

> 14B 本地**不做**：RTX 5060 显存装不下 Q4 量化的 14B（不是慢，是跑不起来），
> 硬测只会 OOM。**"为什么不做"也要写进实验报告**。

**判定标准（决定"自由度"，不是决定"做不做"）**：

| 结论（7B） | agent 形态 | 阶段 3 成本 |
| --- | --- | --- |
| ≥ 80% 且完成率 ≥ 70% | ① **完整**：LLM 自己决定步数和工具（≤5 步） | 3.5 天 |
| 50~80% | ② **半开放**：LLM 选工具，**代码限 3 步** | 2.5 天 |
| < 50%（云端多少都一样） | ③ **受限**：固定 3 步（查证据→查历史→出方案），**LLM 只填参数** | 2 天 |

> 成本已含 §7.6 的 Planner + Critic 双角色（+0.5 天）—— **三种形态都要 Critic** ✅
> （Critic 的作用是"核对依据真实存在"，和模型的规划能力强弱无关 ✅）

**话术硬规定**：形态 ③ 不能说"agent 自主规划"，要说
"agent 固定在 3 个决策点上工作：每步工具由代码保证、参数由模型填写"。

**产出**：`docs/开发指南/14_Agent规划能力实测.md`、`15_数据外发与合规.md`。

### 7.3 LangGraph 图（1 天）

**Planning 模式：Plan-and-Execute（不是 ReAct）**

```text
plan → act → observe → reflect →（回到 plan，≤3 步）→ done
   ↓
为什么选 Plan-and-Execute 而不是 ReAct：
   ReAct 是"边想边做"（每步都重新决定），7B 容易在 3 步后丢失目标 ✅
   Plan-and-Execute 先出一份步骤计划，执行时只填参数，**结构稳定得多** ✅
   —— 这也和"形态 ③ 受限 agent"天然衔接（计划固定，模型只填参数）
```

**状态与停止条件**：

```text
状态：goal / evidence（**每条带来源**）/ steps / budget（token 上限）/ plan
停止：达成 ｜ 步数上限（≤3）｜ token 超预算 ｜ **需要人工**（见下）
```

**Agent 内的 HITL 三个停点（必须写明，否则人不知道在哪介入）**：

| 停点 | 触发 | 之后怎么继续 |
| --- | --- | --- |
| 步数超限 | 3 步还没达成 | 落 `agent_run(status=NEEDS_HUMAN)`，前端显示"需要你决定"，人看轨迹后选择"继续 2 步 / 采纳现有 / 放弃" ✅ |
| Critic 连续两次不通过 | 见 §7.6 | 同上传人工 —— **不让人工被 LLM 卡死** ✅ |
| 方案包含 L2 动作（改描述/改价） | 规划阶段就能判断 | **不自动执行**，转成待批提案（走已有审批链）✅ |

**Memory：明确不做会话记忆**

```text
agent 是【单任务无状态】—— 一次调用一个任务，做完就结束 ✅
   ↓
跨任务的历史由两样东西提供：
   `agent_run`（这次怎么走的）+ `case_entry`（历史上类似问题怎么做的）
   ↓
**这是"外部记忆"，比"对话记忆"可靠** ✅
   因为对话记忆不可检索、不可审计、还会随上下文膨胀 ✅
```

### 7.4 入口 `hub handle <cluster_id>` + `agent_run` 表（0.5 天，**含迁移**）

| **`trace_id`** | 必须写 —— 否则 `hub trace` 查不到这次 agent 的链路 |

| **`proposal_id`**（nullable） | 采纳后回填 —— 让 `agent_run` 与 `action_proposal` 能对上 |
| `created_at` / `finished_at` | — |

③ 超时 5 分钟（3 步 × 每步 100 秒），超时标 FAILED 并记原因

### 7.6 Planner + Critic 双角色（0.5 天）

> 这就是**"多 Agent 协同"在我们项目里的正确形态**：两个角色、一次交互、判定标准明确。

```text
Planner（现有 agent）→ 出方案（steps + evidence + recommendation）
   ↓
Critic（新增，只做一件事）→ 逐条核对：
   ① 方案里引用的每条评价，**是否真的在 evidence 里**（子串校验 ✅ 已有）
   ② 引用的每条案例，**是否真的在 case_entry 里**（阶段 3.5 ✅）
   ③ 方案里的每个数字，**是否来自工具返回**（不是模型自己算的）
   ↓
不通过 → 把"哪里不通过"回给 Planner，**重规划一次**
连续两次不通过 → 转人工（不让人被 LLM 卡死 ✅）
```

**为什么只做两个角色，不做五个**：

```text
多 Agent 的价值在【角色专业化】：各司其职、各有工具、**各有明确的判定标准**
   ↓
我们的任务只有一个（P0 簇处置），工具集是共享的
   ↓
硬拆 5 个角色 → 每个角色都在"猜别人会怎么做"→ 比单 agent 更差
   ↓
而且：**第三个角色没有明确的判定标准** —— 说不出"它判对了还是判错了"，
     那就不是协同，是"多跑几次 LLM" ✅
   ↓
**能说清"为什么不用更多"，比"我用了 5 个 agent"更值钱** ✅
```

**为什么这个角色值得做（不是凑数）**：

```text
① 它和项目的"反幻觉"主题完全一致 —— Critic = **自动化的第二双眼睛**
② 成本可控：方案出完后 +1 次调用，不是每步双跑
③ **可评测**：拦对了几个幻觉 / 误拦了几个（这是有对错的判定）
④ 复用现有能力：子串校验、引用校验、网关——全是现成的
```

**验收（并入 7.5 轨迹评测）**：
① 注入一个"编造依据"的方案 → Critic 必须拦下
② 注入一个"正常方案" → Critic 不能误拦
③ Critic 拦下后，Planner 的第二次方案必须**不再犯同一个错**

## 十四、反跑偏机制

### 14.1 我们这次是怎么偏的（四个征兆）

| 征兆 | 本次表现 | 后果 |
| --- | --- | --- |
| ① "顺手修一下"变成改设计 | `args["topic"]` 顺手塞进工具参数 | 7 个提案全被网关拒 |
| ② "这个更有意思"抢占优先级 | 做了 `today`、经验回灌，没还债 | 债堆到 38 项 |
| ③ "先做了再说" | 验收标准事后补 | "门禁 19/19"成了旧结论 |
| ④ "反正数据要重跑" | mock 数据重生成 4 次 | 所有数字作废 4 遍 |

### 14.2 五条对策

```text
① 顺手修的东西 → **只记台账，不当场做**
② 新想法 → 写进"候选池"，**阶段结束时统一排**（不许中途插队）
③ 代码之前先写【验收命令】；写不出来说明需求没想清
④ 数据改动走"数据改动单"（§十六）
⑤ **动手前先 `grep __tablename__` / `grep "^class"`**
   本次两次以为"要新建表"，实际 `app_user`/`audit_log`/`notification`/`knowledge_entry` 全都有；
   契约层也是"以为在用在，其实是死的"。
   → **"不存在"和"没在用"是两件事** ✅
```

### 14.3 三道闸门

```text
闸门 1｜进入阶段前：属于哪个阶段？验收命令是什么？会让哪个已完成结论失效？
闸门 2｜阶段结束：验收命令必须真的跑过并贴结果（不许"应该没问题"）
闸门 3｜跨阶段：上一阶段验收不过，不进下一阶段
```
