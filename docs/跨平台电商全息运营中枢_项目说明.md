## 1. 问题定义

### 1.1 业务背景

电商商家普遍在多平台开店。面对海量的商品评价数据（文本+买家秀图片），传统人工统计完全失效；而直接把全量数据扔给大模型，不仅成本昂贵，且容易被水军数据污染。商家需要的不只是“看板”，而是一个能自动清洗脏数据、提取多模态特征、发现业务异常，并安全落地动作的**系统级智能体**。

### 1.2 核心痛点

1. **数据噪音与成本**：海量评价中包含大量无意义灌水，全量走大模型会导致 Token 成本失控。
2. **多模态缺失**：大量差评是带图的（如“衣服破洞”），纯文本分析无法理解，且直接留存原图有侵权风险。
3. **执行断层**：分析报告写了，但改详情页、派工单依然靠人工，闭环断裂。AI 直接调工具又存在极大的幻觉与安全风险。

### 1.3 核心问题分层

| 层             | 问题                                 | 平台回答                                                     |
| -------------- | ------------------------------------ | ------------------------------------------------------------ |
| **数据降噪层** | 垃圾数据干扰、成本高昂、图片无法分析 | **前置数据质量引擎(DQE)：ML+规则双轨清洗；多模态沙箱解析（阅后即焚）** |
| **业务分析层** | 单一归因、缺乏业务交叉分析           | **LangGraph 多步 Workflow：复合业务检测（价格背离识别）+ 跨平台问题簇聚类** |
| **执行系统层** | 脚本与系统割裂、AI 乱调工具          | **自研 Tool Gateway（网关鉴权/限流/幂等/风险分级）+ 有界执行链** |
| **评估治理层** | 效果不可量化、线上运行“黑盒”         | **全链路 Trace 追踪 + 离线扰动测试 + 线上 LLM as a Judge**   |

## 2. 项目范围与核心模块

### 2.1 P0 核心模块（对标企业级研发要求）

| 模块                          | 核心能力设计                                                 |
| ----------------------------- | ------------------------------------------------------------ |
| **M1 规则与 ML 前置降噪**     | 引入 **传统机器学习**（TF-IDF+逻辑回归/孤立森林）过滤水军评价与异常评分；包含规则兜底机制（可插拔）。 |
| **M2 多模态沙箱解析**         | 提取图片 URL 进临时沙箱，调用 Vision 模型提取破损/色差特征，**提取后原图物理销毁**。 |
| **M3 多步 Agent 归因链**      | LangGraph 状态机：提取实体 → 意图分类 → 根因匹配，全程依赖 **Pydantic 强制结构化输出**（失败自动重试）。 |
| **M4 复合业务分析**           | 结合文本语义与 pHash 图像对齐，跨平台交叉比对，增加“**价格-评价背离检测**”节点。 |
| **M5 自研工具网关 (Gateway)** | 动态注册工具，定义风险等级（L0-L3）、JSON Schema、限流策略；统一拦截非法调用。 |
| **M6 有界自主执行链**         | 四道校验（参数/权限/幂等/依据）→ 调用工具 → 执行后状态二次确认 → 失败自动回滚。 |
| **M7 自动化调度与治理**       | Redis Stream 驱动任务队列，支持死信队列（DLQ）、定时触发与并发上限控制。 |
| **M8 全链路可观测与评估**     | 全链路 Trace 追踪；离线 30 个动态扰动门禁；**线上挂载 Judge Agent 做质量打分**。 |

## 4. AI / ML 角色与合规边界

### 4.1 传统 ML 与 LLM 的分工
*   **传统 ML（降本）**：处理高频、简单的判断。例如用 `scikit-learn` 训练轻量分类器过滤水军，用 `imagehash` 计算图片相似度。代码轻量，不依赖 GPU。
*   **大模型 LLM（提质）**：处理低频、复杂的语义推理。例如多步归因、跨平台差异分析、工具选择。
*   **可插拔降级**：如果 ML 模型文件加载失败，系统自动切换为纯规则正则过滤，保证主链路永不中断。

### 4.2 多模态合规红线
*   **阅后即焚**：图片仅用于 Vision 模型推理提取文本特征，提取完毕即触发物理删除。
*   **禁止二次开发**：提取特征仅用于内部分析，不用于任何模型微调或对外商业展示。

### 4.3 工具网关强制鉴权（把工具变成系统）
*   LLM 输出必须符合工具预设的 `JSON Schema`，否则网关拒绝执行。
*   工具执行前需校验该次调用的意图依据，防止 Agent 突发奇想乱调。
*   敏感操作（L3 级）网关直接拦截并强制 HITL 人工介入。

## 5. 成功标准（工业化指标）

### 5.1 研发与工程指标
*   **ML 降噪覆盖率**：前置过滤掉 > 60% 的无效数据（极大降低大模型成本）。
*   **结构化输出合规率**：≥ 99%（Pydantic 校验通过率）。
*   **工具调用拦截率**：100%（越权、参数错误全部拦截）。
*   **任务自动触发成功率**：≥ 99%（基于 Redis Stream）。
*   **死信率**：< 1%。

### 5.2 业务与模型指标
*   **多模态特征提取准确率**：≥ 85%（基于人机对齐测试）。
*   **跨平台异常（价格背离）检出率**：≥ 80%。
*   **线上 Judge 评分**：平均分 ≥ 8.5/10（衡量话术合规性与归因合理性）。

## 二、 架构高光设计

如果你在面试时被要求画出架构，画完图后，**挑出以下 4 个亮点主动讲解**，面试官会立刻意识到你是做过系统设计的：

#### 1. DQE 前置降噪（降本增效的护城河）
*   **设计逻辑**：大模型很贵。如果一个月几百万条数据全量走 LLM，系统直接破产。
*   **实现**：数据进来先走 DQE。用 `scikit-learn` 跑一个轻量级分类器，把灌水、无意义评论（占 60%）直接拦截。只把剩下的 40% 核心差评送进 LangGraph 链。
*   **兜底**：如果模型没加载成功，自动降级为“正则规则过滤”，保证业务不中断。

#### 2. 多模态“阅后即焚”沙箱（合规红线）
*   **设计逻辑**：买家秀图片版权不属于商家，不能直接存。
*   **实现**：系统不存原图。图片拉进临时 Docker 沙箱，用 Vision 模型提取出文本标签（例如：`Tag="衣服破损"`），然后立刻物理删除原图。

#### 3. 有界自主执行与 Tool Gateway（安全网关）
*   **设计逻辑**：绝不能让 LLM 瞎调接口。JD 里写的“把工具变成系统”，这就是答案。
*   **实现**：LLM 生成的不是代码，而是带 `JSON Schema` 的意图。所有意图必须经过 Gateway 的**四道防线**：参数强校验 -> 依据是否存在 -> 幂等防重 -> 风险评级。L0-L1 的草稿自动写，L3 的动作直接拦截并生成 HITL 工单。

#### 4. 执行后的“状态回查”（反幻觉最后一公里）
*   **设计逻辑**：LLM 经常“自作聪明”，告诉系统“已经派单成功”，但实际上工具报错了。
*   **实现**：执行链（E4 节点）不信 LLM 的返回，强制执行完工具后，系统用代码去数据库或 API 里查一次。如果发现没派单成功，自动触发回滚。
