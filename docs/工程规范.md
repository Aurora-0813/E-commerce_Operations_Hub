# 工程规范（踩坑换来的规则）

> 这些规则不是"最佳实践抄来的"，是**这个项目里真实踩过、导致返工**的教训。
> 每条都标了"踩过的坑"，方便判断什么时候可以破例。

---

## 一、事实归代码，表达归 LLM

**规则：凡是"事实 / 数值 / 结论"，必须由代码或数据决定；只有"怎么说给人听"才交给 LLM。**

### 踩过的 4 个坑（其实是同一个）

| # | 现象 | 本质 |
| --- | --- | --- |
| 1 | 在提示词里塞"只写可以联系客服办理退换" → 10 条回复一模一样，且对"物流慢"答非所问 | **把"表达"写死了** |
| 2 | `DESC_HINT = {"size": "本款版型偏小"}` → 实际是偏大时写错 | **把"事实"写死了** |
| 3 | 让 LLM "改写整段描述" → "肩宽对不上"变成"肩部宽松适肩" | **让 LLM 改了事实的倾向** |
| 4 | 问"描述里缺什么" → 输出"未说明肩宽问题"（写给商家看的，不是写给买家看的） | **搞错了"说给谁听"** |

### 判据

```text
可以硬编码的：流程 / 规则 / 话术框架
    例："会反馈给工厂核实工艺"（任何质量问题都适用）

不能硬编码的：事实 / 数值 / 结论
    例："本款偏小"（偏大就错）、"降价 5%"（要按规则算）
```

### 正确做法（M5 的提案生成）

```text
代码做：topic → 选工具、处理方向、参数（spu_id / 价格）、问题名
LLM 做：正文怎么写、一句理由

而且"正文里的**事实**"必须先从原文提取、再**原样拼进去**，不许润色：
    hint  = LLM 从评论提取 → "肩宽偏窄，宽肩建议选大一码"
    desc  = 代码拼接 → 原文 + "【补充说明】" + hint
```

**为什么不许二次润色**：润色 = 改变事实的倾向性（投诉会变成卖点）。

## 零、一条判据决定"现在做还是以后做"

> 之前写过两条原则（"结构性的早做" / "纯新增的晚做"），但它们**在中间地带打架**——
> "加一个字段"既像改结构，又像加东西。所以换成一条判据。

**问：将来补的时候，要不要动【已有的代码或数据】？**

```text
要动  → 现在做（否则就是返工）
不动  → 以后做（纯粹是加法）
```

| 改动 | 将来补要动已有的吗 | 结论 |
| --- | --- | --- |
| 加 `prompt_hash` 字段 | **要**：450 行旧数据没值，得重跑 M3 | 现在做 |
| 加 `ToolSpec.outcome_metrics` | **要**：5 个工具类都要改 | 现在做 |
| 加第 6 个工具 | 不要：新文件 + 注册一行 | 以后做 |
| 换 bge 嵌入 | 不要：换一个函数 | 以后做 |
| 调聚类 k | 不要：改一个常数（簇运行时重算） | 以后做 |

**数据类改动的例外**：不是"早做/晚做"，是"**一次做完**"（改一次全链数字作废一次，要攒着改）。

## 一、数据冻结原则（最重要）

**规则：代码可以随便改（重跑几分钟），数据只能改一次（改完全部数字作废）。**

### 为什么

```text
改 generate_mock.py 里一行（销量覆盖 6 → 25）
   ↓ 全局 random 序列后移
write_gold() 的 random.sample 抽到不同金标
write_images() 的 _image_count() 抽到不同张数
   ↓
DQE 重训 → 判定变 → M2/M3 输入变 → 450 条差评变 → 聚类/异常/优先级全变
   ↓
已汇报的所有数字作废，文档要跟着改
```

本轮 M4 就因为这个返工过：为了让"价格背离"能演示，改了 5 个商品的价格 + 问题商品的差评率 → 整条链重跑，M2/M3 的数字全部刷新。

### 所以：新模块开工前，先问"它需要什么数据"

| 模块 | 需要的数据 | 现在有没有 |
| --- | --- | --- |
| M5 决策网关 | 问题清单 + 工具清单 | 问题清单 ✅ / 工具还没有（M5 自己做） |
| M6 执行链 | 动作定义 + 执行日志 | 要新建表，不需要新 mock 数据 |
| M7 调度 | 时间序列 | `sales_daily` 有 90 天 ✅ |
| M8 可观测 | 无 | — |
| **M9 效果复盘** | **干预前 vs 干预后的差异**（DID） | ❌ **没有** |
| M10 运营交互 | 无 | — |

### ⚠️ M9 开工前必须做的一次性数据升级（**不要忘**）

> 原计划写的是"M6 前"，后来想清楚了：**M5/M6 不需要新数据**（它们执行动作、改的是 `platform_product_state`），
> 只有 M9（效果复盘）需要"干预前 vs 干预后"的差异。所以触发条件改成 **M9 前**。

```text
1. 销量覆盖全部 25 个商品（现在只有 PRODUCTS[:6]，导致 reach 退化）
2. 时间结构：某个商品"问题爆发 → 干预 → 改善"
     第 1~4 周：差评率高 + 转化率低
     第 5 周：执行动作（改价 / 改详情页 / 补货）
     第 5~8 周：差评率下降 + 转化率回升
3. 干预记录（哪个商品、哪一周、做了什么动作）→ M6/M9 的 treatment
4. 每个生成器用自己的 random.Random(SEED + 偏移)，隔离随机源
     → 以后改一个生成器不会牵连其他
```

**还有一个更根本的问题要在 M9 前解决**：

```text
我们的动作发生在"现在"（跑代码的时刻），而 mock 数据是固定的历史（截止 2026-10-22）
   ↓
动作之后没有任何数据 → 没有"after"可测 → DID 算不出来
```

三个选项（M9 开工前定）：

| 方案 | 做法 | 诚实度 |
| --- | --- | --- |
| A. 预埋剧本 | mock 里已有"某商品第 5 周改价、之后销量回升"，M9 分析这个剧本 | ⚠️ 系统并没真的执行 |
| B. 事后模拟器 | 执行动作后按新状态生成"未来 7 天"数据 | ✅ 最诚实 |
| C. 推迟 M9 | 等真实数据 | ✅ 最诚实，但少一个模块 |

**改完就冻结，M9 之后不再动数据。** 详见 `generate_mock.py` 顶部的 TODO。

## 二、喂给 ML 的数据，排序必须用**业务主键**

**踩过的坑**：`fetch_reviews` 按 `record.id`（随机 UUID）排序，导致"同样的数据，两次跑出不同的簇"。

```text
✅ ORDER BY platform, platform_review_id   （TB00000000，导入多次都稳定）
❌ ORDER BY record.id                       （gen_random_uuid()，每次导入都变）
```

**关键认知**：`random_state=42` 只保证"同样的数组 → 同样的结果"，**不保证"同样的数据 → 同样的数组"**。输入顺序变了，KMeans 的 k-means++ 初始化就变了。

**适用范围**：任何喂给 `sklearn` / `numpy` / 需要复现的算法。

## 三、upsert 一律用 `upsert_all()`，禁止手写 `set_`

**踩过的坑**：`review_topic` 的 upsert 手写 `set_` 时漏了 `secondary_topics`，`--force` 重跑后多标签**永远是空数组**，但 CLI 统计显示 163 条、**不报任何错**。

```python
# ✅
from hub.persistence.upsert import upsert_all
upsert_all(session, ReviewTopic, rows, key_cols=["record_id"])

# ❌ 手写：加字段时忘了改这里，静默失效
stmt.on_conflict_do_update(set_={"topic": ..., "severity": ...})
```

`upsert_all` 从 `rows[0]` 的 key 自动生成 `set_`，以后加字段不用改它。

**为什么这类 bug 特别危险**：不报错、统计正常、只有直接查库才发现。**必须靠机制，不能靠小心。**

## 四、LLM 任务：先跑"格式测试"再写集成

**踩过的坑**：M3 直接按 JSON 数组集成，结果 3B 在多标签任务上**陷入复读**（`["misship","service","misship","service"...]`，0/10）。

```text
✅ 正确顺序：
   1. 写 tests/check_prompt_xxx.py：10 条手写样例 × 3 种输出格式
   2. 30 秒跑完，选出正确率最高的格式
   3. 再写集成代码

❌ 错误顺序：
   直接写集成 → 跑 450 条 → 发现格式不行 → 改 → 重跑
```

**本项目的实测结论**（3B 模型）：

| 任务 | 可用格式 | 不可用格式 |
| --- | --- | --- |
| 单标签分类 | JSON 对象 `{"topic": ...}` | — |
| 多标签分类 | **行格式** `R1: quality,size \| 3` | JSON 数组里的列表（复读） |
| 图片打标 | JSON 对象 + 占位符 | 带具体值的示例（照抄） |
| 归因 | JSON 对象（不含 R 编号引用） | 让它引用 R 编号（分组会错） |

## 五、改 schema 的顺序：改模型 → 迁移 → 升级 → 再跑

**踩过的坑**：给 `spu_catalog` 加了 `platform` 字段（改模型 + 改导入代码），但**没跑迁移**就跑了全链 → `UndefinedColumn`，导入到商品那一步崩了。

```text
1. 改 models.py
2. alembic revision --autogenerate -m "..."
3. 检查生成的迁移文件（autogenerate 会漏 server_default 之类）
4. alembic upgrade head
5. 再跑业务代码
```

**别攒迁移**：一个阶段一次，不要一个字段一次（但也不要改完一堆模型才跑一次）。

## 六、文档不写死数字

**问题**：现在 `开发思路.md` 里写死了 `3981 / 2318 / 450 / 14 / 4`。数据一变，全要改，而且**没人记得改哪几处**。

**规则**：
- 数字集中在"数据快照"小节，标明**生成时间 + 生成命令**；
- 其他地方只写**结论和量级**（"十几个簇"、"四百多条差评"），不写精确值；
- 精确数字从 `run_all.py` 的输出里取。

## 七、每次交付前的最小检查

```powershell
# 1. 全链能一条命令跑通（最重要的回归）
python scripts\run_all.py

# 2. 关键模块的独立检查
python tests\check_align.py        # 对齐 20 对 / 0 错配
python tests\check_cluster.py      # 簇数 5~15
python tests\check_price.py        # 异常 3~5 个

# 3. 可复现性（连跑两次，结果必须一致）
python -m hub.cli cluster
python -m hub.cli cluster
```

**"在我机器上能跑"不算完成，"清空库能一条命令跑出一样的数字"才算。**
