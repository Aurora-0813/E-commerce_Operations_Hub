# 测试策略（`docs/测试策略.md`）

> **这份文档回答一个问题**："你怎么保证质量？"
> 不是"我们有很多测试"，而是"**哪些测试必须存在、删了会出什么事**"。
>
> 基线：2026-11-01 ｜ `tests/` 下 **58 个** `check_*.py` ｜ 全绿 ✅

---

## 1. 三层结构（按"跑得多快"和"调不调模型"分）

| 组 | 数量 | 特点 | 什么时候跑 |
| --- | --- | --- | --- |
| **quick** | **35** | 不调 LLM、约 35 秒 | **每次改代码都跑** ✅；提交前必跑 ✅ |
| **full** | **58**（含 quick） | 调 LLM/ML/GPU，约 100 秒 | **提交前跑一次** ✅；改核心逻辑必跑 ✅ |
| **probe** | 16 | 手工探针，输出是"打印"不是断言 | 换模型 / 排查时手动跑 |

```powershell
python -B scripts/run_tests.py            # quick
python -B scripts/run_tests.py --group full   # full
python -B scripts/run_tests.py --list     # 看分组
```

**为什么分三组**：quick 是"秒级反馈"，full 要调 7B（慢）✅
**但代价是**：`full` 不常跑 → **stale 测试会攒着** ✅
（实测：`check_classify` 的 `_parse_array` 至少 stale 了几天才被发现 ✅）

## 2. 测试的四种类型（**这是策略的核心**）

### ① 单元/契约测试（最多）

```text
例子：check_gateway（四道防线）、check_contracts（符号级契约）、
      check_normalize / check_simhash / check_rules（DQE 规则）
特点：纯函数、不连库、毫秒级
价值：改一行就知道有没有破
```

### ② **反例测试**（**最容易漏、也最容易骗人**）

```text
例子：check_gateway ⑨b
   "idempotent=False 的工具，连调两次 → **两次都该 EXECUTED**"
   ↓
为什么必须有：**正例证明不了"这个开关被读过"** ✅
   ⑨ 只测了"idempotent=True 时幂等生效" ✅ → 在"无条件幂等"的错误实现下**也能过** ✅ ✗
   ↓
实测踩过：`ToolSpec.idempotent` 声明了，但网关从来没读过它 ✅
   → 只读查询被永久缓存 → 读到旧数据 ✅
```

**规矩**：凡是"开关/布尔字段/配置项"控制了行为，**必须有反例** ✅

### ③ **接线测试**（**第二个最容易骗人的**）

```text
例子：check_agent_wiring
   "guard 的 acquire_slot / apply_critic_verdict **主路径真的调了吗**"
   ↓
为什么必须有：**函数写了 + 测试过了 ≠ 接上了** ✅
   实测：`guard.py` 的 6 个函数全测过、全绿 ✅
   但 `handle()` **根本没调用** `acquire_slot()` / `apply_critic_verdict()` ✅ ✗
   → "测试全绿、功能没接" —— 比"没写"更脏 ✅
   ↓
现在测的是：并发超限时 **拒绝发生在调 LLM 之前**（`llm.calls == 0`）✅
```

### ④ **端到端 / 真机测试**（最少，但最说明问题）

```text
例子：`hub handle 2adf0897 --critic`（真调 7B）
     `python -m scripts.probe_refund_corr`（真数据相关性）
     `build_cases`（真跑一遍看 0 条是正确行为 ✅）
   ↓
为什么必须有：**测试是假的客户端，真机才是真的** ✅
   实测：今天所有 bug 都是"测试过了但真机没跑"暴露的 ✅
```

## 4. 测试的"三条自我约束"

### ① 测试不能"自己打印失败关键词"

```text
`run_tests.py` 的 FAIL_PAT = r"\[FAIL\]|有失败用例|\bFAILED\b|失败 [1-9]\d*\b"
   ↓
测试**自己的文案**会匹配到它 ✅ ✗
   · `check_normalize` 用 ❌ 当测试数据
   · `check_brief` 写"失败 7 次"
   · `check_notify` 断言文案写 "最终 FAILED"
   ↓
**规矩**：测试文案避开 `FAIL / 失败 / ❌`；只有**真断言失败**才输出 `[FAIL]`
```

### ② 测试不能依赖"上一个人留下的状态"

```text
踩过的：
· `check_api_audit` 第一版"取第一个 PENDING 待办" → 上次跑把它拒了 → 这次假红 ✅
· `check_notify [7]` 扫出真实事件后没清 → 残留干扰下一次 ✅
   ↓
**规矩**：测试**自带 fixture、自己清理**（按 id 区间 / TAG 前缀 ✅）
```

### ③ 测试数据不能混进真实业务数据

```text
`run_tests.py` 收尾会跑 `scripts/clean_test_data.py --apply`
   → 只删 **trace_id 前缀**匹配的（`gw-test` / `mcp-` / `test-readonly` ✅）
   → **保护前缀**：`adopt-` / `submit-` / `agent-` / `eval-` / `propose-` ✅
   → **删前复查**：命中保护前缀就 `return 2` 并**拒绝删除** ✅
   ↓
为什么这么小心：首版差点删掉真实的采纳提案 ✅
```

## 5. 什么**不测**（明确说明，不然会被追问）

| 不测 | 为什么 |
| --- | --- |
| **前端** | 0 行代码（阶段 7） |
| **`precision@3`（Case RAG 的检索准确率）** | 需要真实案例库；真实干预 **2026-11-13** 才出结论 |
| **LLM 输出的"质量"** | **明确不做 Judge**（等质检队列有真实人工标注后算 kappa） |
| **并发压力** | 单商家离线系统；agent 并发上限 2 已经够 |
| **多租户隔离** | 没有实现（`tenant_id` 只是字段 ✅） |

## 6. 一句话

```text
"我不是'有很多测试'，我是**知道每条测试在守什么**：
  · 用**反例**守开关（正例证明不了开关被读过）
  · 用**接线测试**守"函数真被调用"（测试绿 ≠ 功能接上）
  · 用**真机跑**守"假客户端骗不了自己"
  · 用**清理脚本**守"测试别污染真实数据"
  ↓
 而 `full` 组不常跑 → **stale 测试会攒着** —— 这是已知的代价，写在 §1 ✅"
```
